# Администрирование Квесты

Отдельная сборка, без PWA и офлайн-кэша. Использует зависимости корневого проекта; новые зависимости не нужны. Роли и доступ проверяются RPC на сервере.

Из корня репозитория:

- `npm run dev -- --config admin/vite.config.mjs` — localhost:5175.
- `npm run build -- --config admin/vite.config.mjs` — admin/dist.
- `npm run preview -- --config admin/vite.config.mjs` — просмотр сборки.
- `npm run test:e2e -- --config admin/playwright.config.mjs` — браузерные тесты собранного admin с синтетическими Auth/RPC. При отсутствии браузера Playwright можно выбрать установленный через `PLAYWRIGHT_ADMIN_CHANNEL=msedge`. Сервер теста использует отдельный порт 4175 и не переиспользует запущенные процессы. Мобильный проект проверяет размер экрана в Chromium, а не настоящий Safari/iOS.

Настройки отдельной среды: VITE_ADMIN_SUPABASE_URL и VITE_ADMIN_SUPABASE_ANON_KEY (только публичный ключ). Не использовать service role. Конфигурация Vite читает env из admin, а не корня приложения; значения не сохраняются в репозитории. Без настроек отображается закрытый экран.

Сессия хранится в sessionStorage под отдельным ключом. Для чтения требуется MFA и активное назначение; регистрация и выдача ролей через этот интерфейс отсутствуют. Начальная настройка TOTP запускается явной кнопкой. QR существует только в памяти экрана. После перезагрузки можно подтвердить незавершённый фактор кодом, если QR ранее добавлен в аутентификатор. Новый фактор при этом не создаётся. Подтверждённые факторы имеют приоритет. При потере QR до сканирования показывается обращение к владельцу; автоматическое удаление факторов и восстановление утраченного MFA не реализованы.

Статус: локальная основа. Реальный TOTP и браузерная приёмка ещё не выполнены. CI, настройки доменов/заголовков безопасности, восстановление MFA и публикация выполняются отдельно. Подробный план и результаты — в Notion OPS-01.

## Проверка сборочной среды и CI

Выпускная сборка требует HTTPS URL без credentials/path/query, нелокальный адрес и публичный publishable key либо legacy JWT с ролью anon. Пустые параметры, HTTP, loopback и service_role отклоняются. Проверка формата не подтверждает подлинность ключа и его соответствие проекту. Test mode разрешает только loopback HTTP и нерабочий синтетический placeholder. Dev без настроек показывает закрытый экран; build без настроек завершается ошибкой.

Admin CI — отдельный frontend workflow: lint, unit/component tests и браузерные сценарии тестовой сборки. Секретов и публикации нет. SQL/RLS и настоящий Auth требуют отдельной интеграционной проверки. Workflow подготовлен локально; на GitHub ещё не запускался.

## Изолированная проверка Auth/TOTP

В PowerShell: `$env:RUN_LOCAL_ADMIN_AUTH='1'; npm.cmd run test -- admin/integration/auth.integration.test.js`.

Нужен запущенный Docker с образами `supabase/postgres:17.6.1.165` и `supabase/gotrue:v2.196.0`. По умолчанию интеграционный сценарий пропущен; контрольный тест генератора TOTP выполняется всегда. Сценарий создаёт отдельную сеть, пустую БД в tmpfs и Auth с случайными тестовыми секретами в памяти. PostgreSQL не публикует порт, Auth публикует случайный порт только на 127.0.0.1. После выполнения удаляются только созданные сценарием контейнеры и сеть. Тест не читает конфигурацию существующего Supabase и не меняет его аккаунты. При аварийном завершении процесса проверяйте оставшиеся ресурсы с префиксом qvesta-auth-test; не удаляйте другие ресурсы Docker.

Проверяет реальный протокол Auth: пароль → aal1, подключение TOTP, отказ неверного шестизначного кода, успешное подтверждение → aal2 и AMR totp, новый вход по паролю → aal1 с сохранённым verified-фактором. Браузерный QR и вызов административного RPC настоящим JWT остаются отдельными интеграционными проверками.

Дополнение: интеграционный сценарий теперь запускает также `public.ecr.aws/supabase/postgrest:v16.1`, применяет шесть административных миграций и проверяет RPC с JWT настоящего Auth. Проверяются отсутствие системной роли, отсутствие MFA, анонимный доступ, повреждённая подпись JWT, разрешённые поиск/карточка, выдача второго владельца со свежим MFA, самоотзыв и прекращение доступа без замены JWT. Доступ к БД через PostgREST выполняется ролью authenticator с переключением в authenticated/anon, а не суперпользователем. Организации и auth.jwt/auth.uid — минимальные синтетические фикстуры, поэтому это не замена прогону всех миграций проекта. UI и браузерное сканирование QR в этот тест не входят.

Полный браузерный прогон: дополнительно установить `RUN_LOCAL_ADMIN_BROWSER=1` (при необходимости `PLAYWRIGHT_ADMIN_CHANNEL=msedge`) и выполнить тот же интеграционный тест. Vite запускается на случайном loopback-порту и проксирует запросы в настоящие одноразовые Auth/PostgREST. Проверяются вход, TOTP, поиск, карточка, мобильный размер 390×844, сохранение сессии после reload, выход и удаление сессии после reload. TOTP для уже подключённого фактора генерируется тестом; сканирование QR физическим телефоном не проверяется. Trace/скриншоты с секретами не сохраняются. После завершения закрываются браузер, Vite, контейнеры и сеть.

Admin CI дополнен отдельным job admin-auth-integration с указанными образами и Chromium. Job подготовлен локально, его успешный запуск в GitHub пока не подтверждён. Проверяется dev frontend через Vite; отдельный frontend job проверяет собранный bundle с синтетическим API.

## Отказы административного доступа

Миграция 20260918070000 сохраняет внешние сигнатуры шести RPC, переносит их реализацию в platform_private и добавляет обёртки. При SQLSTATE 42501 обёртка пишет `QVESTA_ADMIN_DENIAL` через RAISE LOG и повторно выбрасывает исходную ошибку. Структурированная запись содержит только version, event_id, actor_id, action, sqlstate, occurred_at. Нет JWT, параметров запроса, текста поиска или серверного сообщения ошибки. Internal-функции и logger недоступны API-ролям. Успешные действия по-прежнему записываются в транзакционную таблицу аудита.

Это серверный журнал отказов, а не готовый архив аудита с гарантированным сроком хранения. Перед stage нужно проверить доставку, retention и доступ оператора к PostgreSQL logs. Отказы до входа в RPC (неверная подпись JWT, отсутствие EXECUTE у anon), другие SQLSTATE и сбои инфраструктуры здесь не регистрируются — для них требуется отдельная политика журналов API. Обязательные основания команд описаны в следующем разделе. Наличие RAISE LOG не заменяет эти проверки.

## Основания команд

Миграция 20260918080000 добавляет обязательный `p_reason_code` для публичных команд выдачи/отзыва роли, открытия/закрытия обращения и допуска поддержки. Допустимые коды:

- Выдача роли: staff_onboarding, role_change.
- Отзыв роли: staff_offboarding, security_response, role_change.
- Открытие обращения и допуск поддержки: support_request.
- Закрытие обращения: request_resolved, request_cancelled.

Пример: `grant_platform_assignment(..., p_reason_code => 'role_change')`. Свободный текст не принимается. Отсутствие основания отклоняется сервером. Проверка владельца и свежего MFA выполняется раньше записи причины. Таблица platform_command_reasons закрыта RLS/ACL; запись атомарна с командой. Повтор actor_id + command_id обязан сохранять действие и основание; изменение даёт conflict. Причина копируется в командное событие аудита (с command_id); отдельные события снимков назначения продолжают хранить до/после без придуманного основания. Неуспешная команда откатывает причину. Для исторического receipt без основания повтор с новым основанием отклоняется, старые события не переписываются. Bootstrap первого владельца остаётся отдельной доверенной SQL-операцией с session_user, вне этого API.


## Конкурентные команды: bootstrap и поддержка

В `src/services/platformAccessConcurrency.integration.test.js` предусмотрено 12 сценариев на отдельных синтетических базах в локальном контейнере PostgreSQL. Запуск: установить `RUN_LOCAL_PLATFORM_CONCURRENCY=1`, затем выполнить `npm.cmd run test -- src/services/platformAccessConcurrency.integration.test.js`.

К четырём проверкам grant/revoke добавлены восемь: одинаковые и разные команды назначения первого владельца, а также выдача допуска поддержки одновременно с закрытием обращения в обоих порядках. Для каждого варианта проверены commit и rollback первой транзакции; вторая действительно ожидает advisory lock. Проверяются отсутствие дубликатов bootstrap, результат конкурирующей команды, состояние обращения, наличие основания допуска и фактическое право чтения после завершения обеих транзакций. Закрытие прекращает последующие запросы поддержки; уже выполняющийся запрос не прерывается.

Все 12 сценариев прошли локально 18.09.2026 (98,15 с). После прогона временных баз qvesta_admin_test не осталось. Lint и основная сборка прошли с прежними предупреждениями React. Это локальная проверка, не подтверждение GitHub CI или stage. Следующий шаг OPS-01.1 — визуальная приёмка административного интерфейса и подготовка точной конфигурации stage.

## Заголовки статического хостинга admin

Vite генерирует admin/dist/_headers из проверенного origin Supabase. Файл рассчитан на Cloudflare Static Assets без Worker-обработчика. CSP: только собственные скрипты/стили, выбранный HTTPS API (loopback только в test), изображения data: для QR; запрещены frame-ancestors, object, base, form-action и worker. Добавлены DENY, nosniff, no-referrer, запрет камеры/микрофона/геолокации, noindex/nofollow/noarchive и no-store для всех статических ответов. Серверные Auth/RPC-ответы Supabase этим файлом не управляются.

На отдельном хостинге публикуется только admin/dist после сборки --mode staging. Домен, сам ресурс Cloudflare и автоматическая публикация пока не созданы/не подтверждены. _headers не защищает API от неавторизованного запроса: проверка ролей/MFA остаётся серверной. При добавлении Worker-обработчика заголовки нужно выставлять и в его ответах. Источник: https://developers.cloudflare.com/workers/static-assets/headers/

18.09.2026: 21 тест конфигурации/политики, lint, admin test-build и основная сборка прошли. Два браузерных CSP-сценария (desktop/mobile) подтвердили загрузку bundle, поиск и карточку без securitypolicyviolation. Заголовки из собранного файла подставлены в ответ локального preview тестом; обработка файла на Cloudflare ещё не проверена. Подключение QR, настоящий MFA и отказ встраивания с этой политикой требуют отдельных проверок. Публикации не было.

## Отдельный Cloudflare stage

Согласованный стратегией домен: stage-admin.qvesta.ru. Подготовлен admin/wrangler.stage.jsonc, ресурс qvesta-admin-stage, workers_dev=false, preview_urls=false. Только Static Assets из admin/dist, SPA fallback; без Worker-обработчика. Production-конфигурация в этот файл не входит.

Все команды выполняются из корня репозитория. Проверка конфигурации без публикации: `npx wrangler@4.134.0 deploy --config admin/wrangler.stage.jsonc --dry-run`. Реальная публикация той же конфигурации без --dry-run требует отдельного разрешения. Не использовать --no-build: перед публикацией нужно заново собрать staging с настоящим публичным ключом stage. Локальный dry-run 18.09.2026 прошёл с нерабочим синтетическим ключом; этот bundle не готов для реального входа. Первый прогон обнаружил ошибку cwd, исправленную на точку (корень запуска).

Для будущего Workers Builds: root directory — корень репозитория; build command — `npm run build -- --config admin/vite.config.mjs --mode staging`; deploy command — `npx wrangler@4.134.0 deploy --config admin/wrangler.stage.jsonc`; ветка — staging; сборки других веток выключить. Watch paths: admin/*, package.json, package-lock.json. Custom build в Wrangler не заменяет явный build command в настройках Workers Builds. До применения миграций и разрешения на выпуск автоматическую публикацию не включать. Сам ресурс, DNS, привязка Git и переменные в Cloudflare пока не созданы/не проверены.

Основания: https://developers.cloudflare.com/workers/wrangler/configuration/ и https://developers.cloudflare.com/workers/ci-cd/builds/configuration/ . Проверены 23 теста конфигурации/политики и lint/build; после исправления cwd два hosting-теста повторно прошли. GitHub CI дополнен hosting-тестами, но на GitHub ещё не запускался.
