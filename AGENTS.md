# Quest Platform

## Project Context

- Mobile-first PWA для создания и прохождения квестов в реальном мире.
- Основные сценарии: создание квестов, задания, GPS и кодовая проверка, прохождение, статистика, скачивание и офлайн-синхронизация.
- Приоритетный пилот: образовательные, семейные и городские программы в Севастополе.
- Текущий стек: React, Vite, Supabase, IndexedDB, Leaflet и PWA.

## Working Rules

- Перед изменениями изучать относящиеся к задаче файлы и проверять git status.
- Для запроса на анализ или диагностику не изменять файлы, если изменение явно не запрошено.
- Делать минимальные изменения, относящиеся к поставленной задаче.
- Не выполнять commit, push, merge, удаление данных и другие внешние или необратимые действия без явного разрешения.
- Standing authority владельца: после успешной документальной инициализации routine code/refactor/tests/docs и commit/push/PR/merge в утверждённой задаче и безопасном nonproduction процессе не требуют повторного одобрения. Иван назначает scope и исполнителя. Production, существенные изменения стратегии/безопасности и финансовые действия остаются за отдельным решением владельца; конкретный hold задачи сохраняет силу.
- Не изменять package-lock.json без изменения зависимостей.
- Не устанавливать новые зависимости без объяснения необходимости.
- После изменений показывать краткое резюме и список изменённых файлов.

## Secrets and Privacy

- Никогда не читать, не выводить и не копировать содержимое .env, .env.local и других файлов с секретами.
- Не добавлять секреты, токены, ключи Supabase или персональные данные в код, документацию, тесты и логи.
- Правильные ответы и коды заданий не должны передаваться участнику через API или сохраняться в доступном клиенту виде.
- Не журналировать точные координаты, access tokens и персональные данные детей.

## Supabase and Authorization

- Клиентская проверка владельца не является механизмом безопасности.
- Все пользовательские таблицы Supabase должны иметь RLS.
- Изменения базы данных должны оформляться миграциями.
- Изменения таблиц и политик доступа должны сопровождаться тестами RLS.
- Service role key запрещено использовать во frontend.

## Offline Rules

- Повторная синхронизация не должна создавать дубликаты попыток и результатов.
- Offline-события должны быть идемпотентными и иметь client_event_id.
- Обновление IndexedDB не должно удалять несинхронизированные результаты.
- Изменения offline-схемы должны сопровождаться миграцией и тестом восстановления.
- Приложение должно корректно переживать перезапуск браузера и повторную отправку событий.

## Architecture

- Не добавлять новую бизнес-логику непосредственно в крупные React-компоненты.
- Постепенно выделять доменные сервисы, hooks и небольшие UI-компоненты.
- Сервер является источником истины для проверки ответов, лимитов попыток и итоговой статистики.
- Не выполнять прямые REST-запросы из UI, если операция уже может быть реализована через общий data layer.

## Validation

- Использовать только реально существующие команды из package.json.
- После изменения выполнять относящиеся к нему проверки.
- Для текущего проекта минимум: npm run lint и npm run build.
- Не утверждать, что проверка прошла, если команда не запускалась или завершилась ошибкой.
- Если тестов для изменяемой критической логики нет, явно указывать это как риск.

## Code Review Rules

### Security

- Отмечать возможность чтения или изменения чужих приватных квестов и попыток.
- Отмечать раскрытие правильных ответов, кодов, токенов или персональных данных.
- Отмечать изменения Supabase без миграций, RLS и проверки политик.

### Offline synchronization

- Отмечать операции синхронизации, которые при retry создают дубликаты.
- Отмечать миграции IndexedDB, способные удалить локальные данные.
- Отмечать расхождения между локальной и серверной попыткой.

### Quest flow

- Проверять семантику ALL/ANY при сочетании GPS и кода.
- Отмечать ручной ввод GPS-координат, доступный обычному участнику в production.
- Отмечать расчёт доверенной статистики исключительно на клиенте.
- Отмечать изменения лимита попыток, таймеров и завершения без тестов.

## Координация и смена аккаунта

- Иван координирует очередь и передачу; Codex/Work исполняет назначенное задание; владелец Алексей принимает стратегические и production-решения. Роли не предоставляют технических прав. Правила: [docs/process/TWO-ACCOUNT-WORKFLOW.md](docs/process/TWO-ACCOUNT-WORKFLOW.md).
- При смене аккаунта читать репозиторий, актуальный Notion, задачу и [WORKSPACE-HANDOFF](docs/process/WORKSPACE-HANDOFF.md); проверять точный SHA, ветку, git status, worktree и владельцев общих Docker/БД/портов. История другого чата не является контекстом.
- Один worktree и изменяемый контракт закреплять за одной пишущей сессией. Самодостаточную постановку и completion report оформлять по [шаблонам](docs/process/HANDOFF-TEMPLATES.md). Недоступность источника или неизвестного владельца ресурса явно отмечать.
- Согласованные владельцем уточнения переносить в постановку, критерии и отчёт. Разделять реализацию, публикацию и приёмку; результаты прежних запусков помечать reported, собственных повторных проверок — rerun.
- Уточнение постановки не расширяет standing authority на production или иные исключённые действия. Общую БД и чужие незавершённые изменения сохранять.
