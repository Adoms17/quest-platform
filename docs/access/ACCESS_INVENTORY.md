# Инвентаризация текущей модели доступа

Дата: 2026-09-06

Статус: завершена для начала итерации Access Foundation.

## Текущая модель

Сейчас организационной сущности нет. `public.quests.creator_id` одновременно означает автора, владельца и единственного администратора квеста. Политики RLS сравнивают это поле с `auth.uid()`, а часть UI дополнительно повторяет проверку владельца.

`public.profiles.id` имеет связь один-к-одному с `auth.users.id`. Отдельного профиля участника, субпрофиля ребёнка и делегированного управления нет.

## Зависимости от `creator_id`

### База данных

- `supabase/migrations/20260819230000_baseline.sql` создаёт поле и внешний ключ на `profiles`.
- Политики `quests`, `tasks`, `attempts`, `quest_attempts` и `task_attempts` используют владельца квеста для административного доступа.
- `get_participant_tasks`, `start_quest_attempt` и серверная проверка заданий разрешают публичный квест либо квест текущего создателя.
- Тестовые fixtures и staging seed создают квесты с обязательным `creator_id`.

### Frontend

- `QuestCreate.jsx` записывает текущего пользователя в `creator_id`.
- `QuestList.jsx` фильтрует список по `creator_id`, записывает его при копировании и прямом создании копии.
- `QuestEdit.jsx` выполняет клиентскую проверку владельца.
- `QuestStats.jsx` выполняет клиентскую проверку владельца.
- Страницы управления заданиями полагаются на RLS родительского квеста и не имеют отдельной модели разрешений.

Клиентские проверки сохраняются только как UX-оптимизация. После миграции они не могут оставаться источником решения о доступе.

## Текущие границы доверия

- Supabase Auth подтверждает фактического пользователя.
- RLS и security-definer RPC являются серверной границей авторизации.
- React, маршрут, состояние страницы и IndexedDB не являются доверенными.
- RPC жизненного цикла попытки уже владеют критическими записями участника.
- Offline-события дедуплицируются по `client_event_id` и receipts.

## Таблицы и ожидаемое влияние

| Таблица | Текущий субъект | Изменение в первой итерации |
| --- | --- | --- |
| `profiles` | аккаунт пользователя | без изменения семантики; профиль участника появится позже отдельно |
| `quests` | один creator | добавить обязательную после backfill организацию; временно сохранить creator |
| `tasks` | доступ через creator квеста | заменить административную проверку на permission организации |
| `quest_attempts` | user и creator квеста | участник без изменений; просмотр организатором через permission |
| `task_attempts` | user и creator квеста | аналогично `quest_attempts` |
| `attempts` | legacy participant и creator | не расширять; таблица удалена последующей миграцией |

## Обнаруженные риски

1. Политика baseline `Anyone can view tasks` исторически разрешает чтение всех заданий. Поздние RPC ограничивают participant payload, но прямое чтение необходимо отдельно закрыть и проверить, чтобы не раскрывать ответы, коды и будущие координаты.
2. Простая замена `creator_id = auth.uid()` на membership недостаточна: разные действия требуют разных permissions.
3. Security-definer функции должны иметь фиксированный `search_path` и самостоятельно проверять пользователя и область.
4. Backfill должен быть идемпотентным и создавать ровно одну персональную организацию и одно owner membership на владельца.
5. Удалять или делать nullable `creator_id` в первой итерации нельзя: текущий frontend и fixtures зависят от него.
6. Смена организации в UI не должна влиять на серверное решение о доступе.
7. Нельзя смешивать аккаунт, организационное членство и будущий participant profile.

## Граница первой миграции

Первая миграция добавляет организации, членства, стандартные роли, permissions и `quests.organization_id`, выполняет backfill и вводит общие функции проверки доступа. Она не добавляет подписки, приглашения, детские профили, покупки или новый participant flow.

Переход выполняется в два этапа:

1. Совместимость: `creator_id` остаётся заполненным, а новая организация становится дополнительным источником области.
2. Переключение: RLS/RPC и data layer используют permissions; старое поле удаляется только отдельной будущей миграцией.

## Обязательные проверки миграции

- чистая установка и установка поверх текущей схемы;
- повторный backfill не создаёт дубликатов;
- каждый существующий квест получает организацию;
- каждый creator становится owner своей персональной организации;
- пользователь A не видит данные организации B;
- роли действуют только в активном membership;
- отозванное membership прекращает online-доступ;
- текущий владелец сохраняет все прежние возможности;
- participant RPC и offline retry не меняют поведение.
