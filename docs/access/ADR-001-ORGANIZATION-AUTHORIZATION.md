# ADR-001: авторизация через permissions и область организации

Дата: 2026-09-06

Статус: принято для MVP.

## Контекст

Один пользователь может работать в нескольких организациях и иметь разные обязанности. Иерархическое число уровня роли не выражает области действия и приводит к ошибкам вида «роль выше — значит доступно всё». Тариф также не является ролью.

## Решение

Сервер разрешает действие только при одновременном выполнении условий:

1. пользователь имеет активное членство в нужной организации;
2. хотя бы одна назначенная роль содержит требуемый permission;
3. ресурс относится к этой организации;
4. продуктовая возможность доступна по entitlement, если действие тарифицируется.

В MVP применяются только разрешающие стандартные роли. Явного `deny`, наследования пользовательских ролей и глобального числового уровня роли нет.

## Идентификаторы permissions первой итерации

- `organization.read`
- `organization.manage`
- `members.read`
- `members.manage`
- `billing.read`
- `billing.manage`
- `quests.read`
- `quests.create`
- `quests.update`
- `quests.delete`
- `quests.publish`
- `participants.read`
- `participants.manage`
- `quest_runs.conduct`
- `quest_stats.read`
- `quest_stats.delete`
- `access_grants.manage`

Идентификаторы стабильны и хранятся как данные. Изменение отображаемого названия роли не меняет permission key.

## Серверный контракт

Общие функции проверки должны:

- принимать идентификатор организации или ресурса и permission key;
- использовать `auth.uid()` и не доверять user id из клиента;
- возвращать false для анонимного пользователя, неизвестного permission и неактивного membership;
- иметь фиксированный `search_path`;
- не выдавать содержимое ролей через security-definer без необходимости;
- использоваться одинаково в RLS и RPC.

## Совместимость

Во время перехода creator существующего квеста получает owner membership. `creator_id` сохраняется до перевода frontend, RPC, seed и тестов. Это поле не используется для выдачи новых делегированных прав после переключения RLS.

## Последствия

- Появляется явная и тестируемая область авторизации.
- Делегирование не требует передачи владения квестом.
- Тарифы можно проверять независимо от ролей.
- Схема и тесты становятся сложнее, поэтому permissions добавляются поэтапно.
- Платформенные роли и participant supervision будут отдельными областями и не должны переиспользовать organization membership без явного решения.
