# Выпуск Access Foundation

## Предварительные условия

- создана резервная копия базы целевого окружения;
- применены все предыдущие миграции;
- frontend ещё не опубликован раньше миграций `20260907010000`–`20260907020000`;
- доступны два тестовых аккаунта из разных организаций;
- проверены `npm test`, `npm run lint`, `npm run build`, `npm run test:e2e` и `npx supabase test db`.

## Порядок stage rollout

1. Зафиксировать количество `quests`, уникальных `creator_id` и квестов без организации до миграции.
2. Применить миграции базы.
3. Проверить, что каждый квест имеет `organization_id`.
4. Проверить, что каждый прежний creator имеет personal organization, active membership и owner role.
5. Выполнить smoke под владельцем: список, создание, копирование, редактирование, задания и статистика.
6. Добавить второе owner membership тестовому пользователю и проверить совместное управление.
7. Под посторонним аккаунтом проверить отсутствие приватного квеста, заданий и статистики.
8. Опубликовать frontend той же версии.
9. Наблюдать ошибки RLS, создание профилей и квестов, не записывая токены или персональные данные.

## Go / No-Go

Go допускается, если:

- нет квестов без организации;
- прежние владельцы сохраняют доступ;
- совместный владелец получает доступ через membership;
- посторонний пользователь не получает данные ни таблицами, ни RPC;
- создание нового аккаунта создаёт профиль, организацию и owner membership;
- создание квеста через новый и совместимый старый payload работает.

No-Go при любой межорганизационной утечке, orphan-квесте, ошибке provisioning нового профиля или потере прежнего доступа владельца.

## Восстановление

Миграции намеренно сохраняют `creator_id` и прежние данные, поэтому предпочтительный recovery — исправляющая forward migration и возврат frontend на предыдущую версию.

Не следует вручную удалять новые таблицы после появления организационных данных: это может уничтожить назначения ролей. Если проблема обнаружена до записи новых организационных данных, восстановить базу из предрелизной копии и вернуть предыдущий frontend. Если данные уже создавались, остановить rollout, оставить frontend предыдущей версии и подготовить отдельную проверенную миграцию исправления.

## Проверки после выпуска

- количество квестов до и после совпадает;
- `organization_id is null` возвращает ноль;
- нет дубликатов `(organization_id, user_id)`;
- нет дубликатов `(membership_id, role_id)`;
- нет personal organization без active owner membership;
- server/RPC и offline-сценарии проходят smoke;
- логи не содержат access tokens, точные координаты или детские персональные данные.
