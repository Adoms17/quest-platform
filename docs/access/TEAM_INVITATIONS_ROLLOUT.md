# Команда организации и приглашения

## Назначение

Итерация добавляет управление сотрудниками в области выбранной организации. Пользователь может одновременно владеть личной организацией и состоять в других организациях по приглашению. Совпадающие названия не означают совпадающие сущности: интерфейс различает их по `organization_id` и помечает как «личная» или «по приглашению».

## Модель безопасности

- Читать команду может активный участник с `members.read`.
- Создавать и отзывать приглашения, менять роли и отзывать членство может участник с `members.manage`.
- Приглашение привязано к нормализованному email, имеет срок действия и принимается один раз.
- В базе хранится SHA-256-хеш токена; исходный токен возвращается только при создании ссылки.
- Роль `owner` нельзя назначить приглашением, изменить или отозвать через обычный team flow. Для передачи владения потребуется отдельный процесс.
- Серверные RPC и RLS являются источником истины; ограничения интерфейса не считаются механизмом безопасности.
- Аудит не содержит токен, хеш токена или email приглашения.

## Локальный запуск

1. Запустить Docker Desktop.
2. Выполнить `npx supabase start` и дождаться готовности PostgreSQL.
3. Убедиться, что `.env.local` содержит локальный `API_URL` как `VITE_SUPABASE_URL` и локальный anon/publishable key как `VITE_SUPABASE_ANON_KEY`. Никогда не использовать service role key во frontend.
4. Запустить `npm run dev -- --host 127.0.0.1 --port 5174`.
5. Если PostgREST после аварийного завершения не видит уже применённую миграцию, выполнить `notify pgrst, 'reload schema';` в локальной базе. Не сбрасывать базу ради обновления schema cache.

## Smoke-тест

1. Войти под владельцем и открыть `/organization/team`.
2. Проверить, что в списке есть владелец, а изменение и отзыв его роли недоступны.
3. Создать приглашение для другого email с одной или несколькими ролями.
4. Проверить, что одноразовая ссылка показывается и копируется.
5. Открыть ссылку в отдельном профиле браузера и войти с тем же email.
6. Проверить автоматический возврат на страницу принятия и появление приглашённой организации.
7. Убедиться, что личная организация отмечена как «личная», а добавленная — как «по приглашению», без повторов `organization_id`.
8. Под владельцем изменить роли приглашённого сотрудника и обновить страницу.
9. Отозвать доступ и проверить, что организация исчезла из активного контекста сотрудника.
10. Создать второе приглашение и отозвать его до принятия; отозванная ссылка не должна давать доступ.

## Автоматические проверки

- `npx supabase test db`
- `npm test`
- `npm run lint`
- `npm run build`
- `npm run test:e2e`

Критические pgTAP-сценарии проверяют межорганизационную изоляцию, запрет роли владельца, email-binding, одноразовость и идемпотентность принятия, отзыв членства и отсутствие секретов в аудите.

## Rollout

1. Применить миграции на stage отдельным workflow с dry-run.
2. Развернуть frontend только после успешных тестов миграций и RLS.
3. Провести smoke двумя отдельными аккаунтами.
4. Проверить события аудита без вывода персональных данных и токенов.
5. После stage approval повторить процесс для production.

No-Go: возможность назначить `owner` обычным приглашением, доступ к чужой организации, повторное создание членства при retry, открытый токен в базе/логах или потеря последнего владельца.
