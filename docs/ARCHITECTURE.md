# Архитектура Quest Platform

## Обзор

Quest Platform — клиентское React PWA. Интерфейс работает с Supabase для авторизации и удалённых данных, а также с IndexedDB для скачанных квестов, локальных попыток и очереди результатов. При восстановлении сети `sync.js` отправляет накопленные данные в Supabase.

```text
Пользователь
  ↓
React UI
  ├→ Supabase
  └→ IndexedDB → sync.js → Supabase
```

Схема показывает направления взаимодействия, а не границу доверия: frontend и локальное хранилище не являются доверенным источником данных.

## Маршрутизация и UI

`src/App.jsx` использует `BrowserRouter`. Страницы `Login`, `QuestList`, `QuestCreate`, `QuestEdit`, `QuestPlay`, `QuestStats`, `Downloads`, `TaskManager` и `TaskForm` подключены через `React.lazy`. Это создаёт маршрутное разделение кода; `Suspense` показывает общий индикатор загрузки.

`ProtectedRoute` закрывает маршруты, требующие клиентской сессии. Он улучшает UX, но не является механизмом авторизации данных: сервер всё равно обязан проверять права пользователя.

`Layout` добавляет `Navbar` вокруг защищённых страниц. Переиспользуемые элементы находятся в `src/components`, а сценарии страниц — в `src/pages`.

## Lazy Route Error Boundary

`LazyRouteErrorBoundary` расположен снаружи `Suspense`. Он перехватывает rejected dynamic import и ошибки рендеринга ленивого маршрута, логирует исходную ошибку и предлагает явную перезагрузку. Автоматической перезагрузки нет, поэтому boundary не создаёт бесконечный reload-loop.

Это защита последнего уровня при запросе удалённого hashed-чанка после deployment, а не замена корректной стратегии публикации ассетов.

## Supabase Auth и доступ к данным

Клиент Supabase создаётся в `src/supabaseClient.js` из `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. `App` восстанавливает сессию через Supabase Auth и подписывается на её изменения. Страницы и `sync.js` обращаются к Supabase через JavaScript Client.

Схема Supabase версионируется в `supabase/migrations`. Серверные RPC отвечают за жизненный цикл попытки, проверку заданий и повторную доставку событий; участнику закрыты прямые записи в таблицы попыток. pgTAP-тесты в `supabase/tests/database` проверяют RLS, приватность профилей, серверную проверку, согласованность квеста и задания, GPS/hybrid-правила, доверенное время и идемпотентность. Соответствие реально развёрнутой схемы репозиторию всё равно подтверждается через migration inspection и тесты связанного окружения.

Организационный доступ строится через `organizations`, активные `organization_memberships`, назначенные `roles` и стабильные permission keys. Один пользователь может состоять в нескольких организациях и быть владельцем нескольких организаций. `has_organization_permission` и `has_quest_permission` являются общими серверными проверками для RLS и RPC. Поле `quests.creator_id` временно сохраняется для совместимости и аудита происхождения, но больше не определяет административный доступ в одиночку.

Frontend загружает разрешённые организации через общий data layer и хранит текущий выбор отдельно для каждого аккаунта. Этот выбор только ограничивает рабочий контекст интерфейса: сервер повторно проверяет организацию и permission для каждого запроса.

Доступ участника к закрытому квесту выдаётся отдельно от роли в организации.
Организатор создаёт персональное приглашение по email, общую ссылку или короткий
код. После активации любого из этих способов сервер создаёт нормализованное право
в `quest_access_grants`, которое учитывается функцией `can_access_quest`.
Открытые токены и коды не хранятся в базе: `quest_access_credentials` содержит
только SHA-256-хеш. Для коротких кодов действует серверное ограничение неудачных
попыток на один аккаунт. Отзыв способа входа запрещает новые активации, а отзыв
уже выданного права немедленно блокирует новые онлайн-действия участника.
Секреты, сохраняемые организатором для повторного копирования, шифруются в
браузере с помощью AES-GCM; незашифрованные данные из прежнего `localStorage`
переносятся при первом чтении и удаляются.
Подробности, инварианты безопасности и история решений ведутся в
[технической документации Notion](https://app.notion.com/p/3d7511103a9a81679de7fd3e43ce4e0e).

## IndexedDB: db.js

`src/services/db.js` открывает базу `QuestPlatformDB` версии 10 через `idb`. Слой хранит очищенные offline-пакеты, метаданные скачивания, минимальные профили участников, pending events и локальные quest attempts. Пакет привязан к профилю участника и имеет 24-часовой TTL последней серверной проверки доступа. Локальный список доступных квестов строится только из свежих пакетов текущего пользователя.

Текущая `upgrade`-логика изменяет существующие object stores на месте и создаёт только отсутствующие stores или индексы. Переходы не пересоздают stores и не удаляют несинхронизированные события. Любое следующее изменение `DB_VERSION` должно сохранять этот подход и сопровождаться браузерным recovery-тестом обновления.

## Синхронизация: sync.js

`src/services/sync.js` получает несинхронизированные записи из IndexedDB, сопоставляет локальные и серверные попытки, отправляет данные в Supabase, отмечает успешные записи и очищает синхронизированные результаты. Для повторов предусмотрен `syncPendingResultsWithRetry`. После успешной синхронизации отправляется событие `quest-sync-complete`.

Повторная отправка использует стабильный `client_event_id`. События одной попытки отправляются в порядке локальных идентификаторов. Уникальные ограничения, server-owned RPC и receipts обеспечивают дедупликацию и восстановление состояния после потерянного ответа; соответствующие сценарии покрыты unit и pgTAP-тестами.

## Online data flow

```text
React page
→ Supabase Auth/session
→ Supabase query or mutation
→ обновление React state
→ при необходимости сохранение данных квеста в IndexedDB
```

При online-прохождении страницы читают и изменяют удалённые данные непосредственно через Supabase Client. Скачиваемые квесты дополнительно сохраняются локально.

## Offline data flow

```text
Скачанный квест из IndexedDB
→ локальная попытка и pending result
→ восстановление сети
→ syncPendingResultsWithRetry
→ Supabase
→ отметка/очистка синхронизированных локальных записей
```

Событие `online` в `App` инициирует retry при наличии сессии. Страницы прохождения показывают состояние сети и фактический режим проверки. `Online` и политика `block` запрещают offline-старт. `Hybrid` предварительно проверяет PBKDF2 verifier и локально учитывает каждую попытку; `Secure online / allow_pending` сохраняет ввод без определения результата. Сервер подтверждает итог во всех режимах.

После reload восстанавливаются профиль, полный безопасный набор заданий, число попыток, предварительные статусы и очередь. Локально успешные и исчерпавшие лимит задания входят в предварительную статистику; интерфейс явно сообщает, что сервер может изменить итог после синхронизации.

## Карты и геопозиция

Online-карты построены на Leaflet и загружаемой OSM-подложке. Общая карта
показывает только разрешённые сервером места и кодирует статус цветом. Карта
задания показывает номер, радиус проверки и текущую позицию.

После явного действия пользователя `watchPosition` обновляет координаты до
остановки или ухода со страницы. Координаты пользователя не сохраняются и не
журналируются. Единый информационный блок online/offline показывает расстояние,
точность, направление, азимут и попадание в зону.

Offline используется локально генерируемая SVG-схема без тайлов. Открытие точки
во внешнем приложении, копирование и Web Share дополняют схему. Статическое
изображение улиц намеренно отложено: публичные OSM-тайлы нельзя включать в
offline-пакет. Решение зафиксировано в ADR-004 в
[технической документации Notion](https://app.notion.com/p/3d7511103a9a81679de7fd3e43ce4e0e).

## PWA и service worker

`vite-plugin-pwa` с `registerType: 'autoUpdate'` генерирует service worker. Workbox precache включает собранные JS/CSS/HTML и перечисленные статические форматы. Production-сборка создаётся в `dist`.

Для PWA в production нужен HTTPS. При rollout желательно временно сохранять предыдущие hashed assets, чтобы открытые вкладки могли завершить загрузку старых lazy-чанков.

## Тестирование

Vitest и React Testing Library покрывают компоненты, стабильность эффектов и Error Boundary. Каталог `e2e` содержит Playwright smoke tests для страницы входа, защищённых маршрутов, IndexedDB recovery и мобильных viewport-профилей. Отдельные сценарии под флагом `RUN_LOCAL_SUPABASE_E2E` используют локальный Supabase и проверяют реальную авторизацию, participant flow, идемпотентную offline-синхронизацию, управление профилями и составом групп.

## CI и security tooling

GitHub Actions job `validate` запускает установку зависимостей, audit, lint, Vitest, build и Playwright. Dependabot настроен файлами репозитория для npm и GitHub Actions.

CodeQL включён через GitHub Default Setup, поэтому отдельный CodeQL workflow в репозитории отсутствует. Общий ruleset защищает `main` и `staging`, требует pull request, `validate`, линейную историю и результаты CodeQL. GitHub Environment `production` требует ручного подтверждения; `production` и `staging` ограничены защищёнными ветками. Secret scanning/push protection и Codex Review не версионируются вместе с кодом и проверяются отдельно.

## Границы доверия

- Frontend, React state, IndexedDB и данные, присланные клиентом, нельзя считать доверенными.
- Anon/publishable key является публичным и попадает в клиентский bundle.
- Правильные ответы, лимиты попыток и итоговая статистика должны проверяться доверенной серверной стороной.
- Для пользовательских таблиц обязательны корректные политики Supabase RLS.
- Миграции и RLS tests версионируются в репозитории; их применение к конкретному удалённому окружению необходимо подтверждать отдельно.
- `service_role` key запрещено использовать во frontend.

## Известные ограничения и технический долг

- Запросы не отменяются при быстрой смене маршрута; поздний ответ теоретически может перезаписать более новое состояние.
- Полный production smoke пока не автоматизирован.
- IndexedDB обновляется без пересоздания object stores; регрессию контролирует Playwright-сценарий сохранности квеста, попытки и pending-события при обновлении версии.
- Offline retry защищён `client_event_id`, receipts, серверными тестами и авторизованным browser E2E; до закрытия Gate E остаётся реальная Android/iOS матрица.
- Frontend развёрнут отдельными Cloudflare Workers для staging и production; их build variables и branch control остаются внешней конфигурацией.
- Static/offline map с улицами требует собственного или лицензированного источника и управления квотой пакета.
- Удалённые изображения и медиа ещё не гарантированно помещаются в offline-пакет как автономные blob-ресурсы.
- Полная мобильная матрица на реальных Android/iOS устройствах остаётся обязательной перед закрытием Gate E.
