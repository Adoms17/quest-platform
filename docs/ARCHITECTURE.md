# Архитектура Quest Platform

## Обзор

Quest Platform — клиентское React PWA. Интерфейс работает с Supabase для авторизации и удалённых данных, а также с IndexedDB для скачанных квестов, локальных попыток и очереди результатов. При восстановлении сети `sync.js` отправляет накопленные данные в Supabase.

```text
Пользователь
  ↓
React UI
  ├→ Supabase
  └→ IndexedDB → sync.js → Supabase
```

Схема показывает направления взаимодействия, а не границу доверия: frontend и локальное хранилище не являются доверенным источником данных.

## Маршрутизация и UI

`src/App.jsx` использует `BrowserRouter`. Страницы `Login`, `QuestList`, `QuestCreate`, `QuestEdit`, `QuestPlay`, `QuestStats`, `Downloads`, `TaskManager` и `TaskForm` подключены через `React.lazy`. Это создаёт маршрутное разделение кода; `Suspense` показывает общий индикатор загрузки.

`ProtectedRoute` закрывает маршруты, требующие клиентской сессии. Он улучшает UX, но не является механизмом авторизации данных: сервер всё равно обязан проверять права пользователя.

`Layout` добавляет `Navbar` вокруг защищённых страниц. Переиспользуемые элементы находятся в `src/components`, а сценарии страниц — в `src/pages`.

## Lazy Route Error Boundary

`LazyRouteErrorBoundary` расположен снаружи `Suspense`. Он перехватывает rejected dynamic import и ошибки рендеринга ленивого маршрута, логирует исходную ошибку и предлагает явную перезагрузку. Автоматической перезагрузки нет, поэтому boundary не создаёт бесконечный reload-loop.

Это защита последнего уровня при запросе удалённого hashed-чанка после deployment, а не замена корректной стратегии публикации ассетов.

## Supabase Auth и доступ к данным

Клиент Supabase создаётся в `src/supabaseClient.js` из `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. `App` восстанавливает сессию через Supabase Auth и подписывается на её изменения. Страницы и `sync.js` обращаются к Supabase через JavaScript Client.

В репозитории присутствуют клиентские операции с квестами, заданиями и попытками. Миграции Supabase, определения таблиц и тесты политик RLS отсутствуют, поэтому фактическую production-схему и корректность RLS по этому коду подтвердить нельзя.

## IndexedDB: db.js

`src/services/db.js` открывает базу `QuestPlatformDB` версии 6 через `idb`. Слой хранит скачанные квесты, метаданные скачивания, pending results и локальные quest attempts. Экспортируемые функции отвечают за чтение, запись, очистку и отметку синхронизации.

Текущая `upgrade`-логика при переходе со старой версии удаляет существующие object stores и создаёт их заново. Следующее изменение `DB_VERSION` без безопасной миграции может удалить скачанные квесты и несинхронизированные результаты. Поэтому изменение схемы должно сопровождаться миграцией, backup/recovery-сценарием и тестами обновления.

## Синхронизация: sync.js

`src/services/sync.js` получает несинхронизированные записи из IndexedDB, сопоставляет локальные и серверные попытки, отправляет данные в Supabase, отмечает успешные записи и очищает синхронизированные результаты. Для повторов предусмотрен `syncPendingResultsWithRetry`. После успешной синхронизации отправляется событие `quest-sync-complete`.

Повторная отправка должна оставаться идемпотентной. Текущий репозиторий не содержит отдельного серверного контракта или миграций, позволяющих полностью доказать защиту от дублей на стороне базы.

## Online data flow

```text
React page
→ Supabase Auth/session
→ Supabase query or mutation
→ обновление React state
→ при необходимости сохранение данных квеста в IndexedDB
```

При online-прохождении страницы читают и изменяют удалённые данные непосредственно через Supabase Client. Скачиваемые квесты дополнительно сохраняются локально.

## Offline data flow

```text
Скачанный квест из IndexedDB
→ локальная попытка и pending result
→ восстановление сети
→ syncPendingResultsWithRetry
→ Supabase
→ отметка/очистка синхронизированных локальных записей
```

Событие `online` в `App` инициирует retry при наличии сессии. Страницы прохождения также учитывают `navigator.onLine`. Перезапуск браузера переживается благодаря IndexedDB, но полнота recovery-сценариев ограничена существующими тестами.

## PWA и service worker

`vite-plugin-pwa` с `registerType: 'autoUpdate'` генерирует service worker. Workbox precache включает собранные JS/CSS/HTML и перечисленные статические форматы. Production-сборка создаётся в `dist`.

Для PWA в production нужен HTTPS. При rollout желательно временно сохранять предыдущие hashed assets, чтобы открытые вкладки могли завершить загрузку старых lazy-чанков.

## Тестирование

Vitest и React Testing Library покрывают компоненты, стабильность эффектов и Error Boundary. Каталог `e2e` содержит Playwright smoke tests для страницы входа, защищённого и неизвестного маршрута. E2E используют production preview и тестовые Supabase values, но не выполняют реальную авторизацию.

## CI и security tooling

GitHub Actions job `validate` запускает установку зависимостей, audit, lint, Vitest, build и Playwright. Dependabot настроен файлами репозитория для npm и GitHub Actions.

CodeQL включён через GitHub Default Setup, поэтому отдельный CodeQL workflow в репозитории отсутствует. В настройках GitHub также включены ruleset для `main`, обязательная проверка `validate`, secret scanning/push protection и Codex Review. Эти настройки не версионируются вместе с кодом и должны отдельно проверяться перед production-релизом.

## Границы доверия

- Frontend, React state, IndexedDB и данные, присланные клиентом, нельзя считать доверенными.
- Anon/publishable key является публичным и попадает в клиентский bundle.
- Правильные ответы, лимиты попыток и итоговая статистика должны проверяться доверенной серверной стороной.
- Для пользовательских таблиц обязательны корректные политики Supabase RLS.
- Фактические политики RLS, миграции и RLS tests в текущем репозитории не представлены.
- `service_role` key запрещено использовать во frontend.

## Известные ограничения и технический долг

- E2E не покрывают авторизованные сценарии.
- Запросы не отменяются при быстрой смене маршрута; поздний ответ теоретически может перезаписать более новое состояние.
- Миграции Supabase и тесты RLS отсутствуют в репозитории.
- Текущая IndexedDB upgrade-логика пересоздаёт object stores; до следующего повышения `DB_VERSION` её необходимо заменить безопасной миграцией.
- Offline retry должен оставаться идемпотентным; серверная гарантия дедупликации текущими файлами не доказана.
- Production hosting пока не документируется как уже настроенный.
- Серверные проверки ответов, лимитов и доверенной статистики текущим репозиторием не подтверждены.
