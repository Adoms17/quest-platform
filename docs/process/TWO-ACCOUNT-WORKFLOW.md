## Ответственность и источники

Иван ведёт очередь, зависимости, границы, критерии и ревью; Codex/Work выполняет только назначенную задачу и передаёт проверяемый результат. Владелец может уточнить постановку напрямую; исполнитель записывает согласованное изменение и последствия, Иван принимает по актуальным критериям. Уточнение не разрешает автоматически commit/push/merge/deploy или финансовую операцию. Применимое разрешение записывается отдельно; AGENTS.md сохраняет силу.

- AGENTS.md — постоянные обязательные правила.
- Notion — концепция, бизнес-правила, решения, актуальный план и [backlog](https://app.notion.com/p/66f9d031b6394253a2574fb14865c850).
- Самодостаточная задача — objective/why/context/scope/out of scope/AC/constraints/validation/docs/completion по [шаблону](HANDOFF-TEMPLATES.md). GitHub Issue, если создан, ссылается на каноническую задачу; две независимые очереди не вести.
- Репозиторий — технические контракты, миграции, тесты; docs/tasks — связанные технические постановки и evidence.
- PR — diff, проверки и ревью. GitHub Project необязателен.
- [WORKSPACE-HANDOFF.md](WORKSPACE-HANDOFF.md) — краткий текущий вход, эквивалент PROJECT_STATE; второй файл состояния не создавать.

При расхождении сверить время, SHA, среду и вид доказательства, записать разницу. Не заменять поздний факт старым «следующим шагом» из истории. При недоступном Notion указать ограничение и предложения в отчёте; не заявлять обновление. Секреты, env, реальные токены и персональные данные не читать и не включать в передачу.

## Цикл и изоляция

Backlog → Ready → In progress → Review → Done. Ready означает исполнимость без предыдущего чата: заданы baseline SHA, worktree/ветка, исполнитель, область, разрешения, зависимости, критерии и проверки. Если неизвестен владелец необходимого общего ресурса, зависимое действие блокируется до уточнения.

По умолчанию отдельный worktree от точного commit и одна пишущая сессия на worktree/контракт. Незакоммиченные изменения не переносятся автоматически. Параллельный писатель в те же файлы запрещён; передача владения фиксируется. Worktree не изолирует Docker, БД и порты. Не выполнять reset/clean/stash чужой работы, удаление копий, остановку неизвестных процессов или reset общей БД.

## Начало и завершение сессии

1. Прочитать AGENTS, это руководство, WORKSPACE-HANDOFF, задачу, последний completion report и актуальные связанные страницы Notion.
2. Проверить cwd, hostname, ветку, полный HEAD, tracking, git status и worktree list. Сверить ожидаемый baseline, чужие изменения и владельца пишущей сессии. Fetch выполнять только в разрешённом контексте; checkout занятой копии не переключать.
3. Проверить доступы текущего аккаунта без вывода секретов. Git author и общая Windows CLI-сессия не доказывают отдельную идентичность аккаунта. При отсутствии доступа честно ограничить область.
4. Зафиксировать ресурсную таблицу: абсолютный app/config path, порт/PID и владелец сессии; Docker container/БД, назначение, применённая схема и владелец. Неизвестное отметить unknown; не присваивать ресурс себе по наличию порта.
5. Выполнить назначенную работу и профильные проверки. Каждое evidence содержит дату, SHA, среду, команду/действие, результат, ссылку и ограничения. Reported — прочитанный старый отчёт; rerun — реально выполненная этой сессией проверка. Synthetic API, SQL claims, настоящие Auth/MFA, stage HTTP и финансовое execute — разные доказательства.
6. Передать completion report с diff/commit/PR, git status, файлами и Notion-ссылками, остаточными рисками и ресурсами. Иван проводит ревью; стратегическое решение и production Go остаются у владельца.

## Проверки и выпуск

Использовать существующие команды package.json. Минимум после изменений: npm.cmd run lint и npm.cmd run build; ошибки/пропуски не скрывать. Дополнительные проверки выбирать по фактическому diff. Документальная правка не требует выдуманных функциональных тестов. Не устанавливать зависимости и не копировать env без необходимости и применимого разрешения.

Изменение схемы требует миграций и RLS-тестов; offline — проверки client_event_id, retry, сохранности очереди и recovery. Интеграционный harness может создавать временную БД: предварительно проверить его цель и изоляцию, не reset общей базы. Удалённая миграция — отдельный разрешённый выпуск с историей, составом и preview. Не запускать общий db push ради инвентаризации.

Статусы вести раздельно: implementation (код/документы, SHA), deploy (куда и что опубликовано), acceptance (какие сценарии реально приняты). Done/merged/успешный build не означают stage acceptance или production Go. Перед push/merge проверить автоматические публикации, включая Cloudflare. Ручной Supabase workflow не исключает frontend-автодеплой. Неизвестные production-эффекты — блокер соответствующего действия, не повод менять настройки без разрешения.
