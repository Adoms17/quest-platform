# PROD-PAY-03 — обычная подписка и автоматический зачёт

Статус 30.09.2026: stage-цепочка обычной тестовой подписки и автоматического зачёта подтверждена. После исправления идентификатора чек восстановлен GET-сверкой; повтор безопасен, расписание выключено. Production не менялся.

## Подтверждено по коду
- Обычный заказ без возврата использует subscriptionSettlementQueue.js → list_due_subscription_settlements → runPrepaymentSettlement. Условие срока проверяется повторно под блокировкой заказа; первое отправление расходует claim, неопределённый результат восстанавливается сверкой без нового POST.
- sandbox-reconcile содержит эту фазу, выключенную по умолчанию флагами SETTLEMENT_RECONCILIATION и SETTLEMENT_DISPATCH. Включать общий batch для приёмки одного заказа нельзя: он может выбрать другие подходящие заказы.
- Существующее расписание quest-stage-order-reconciliation вызывает sandbox-reconcile-order, который проверяет платёж/выдачу, но не зачёт. Оно прекращает обработку после applied; использовать его как доказательство автоматического зачёта нельзя.
- Приёмка PROD-PAY-02 завершена отдельно: полный возврат Business; этот заказ не использовать повторно.

## Итерация 03.1 — ограниченный обработчик
Добавить отдельный маршрут обычного зачёта одного заказа, использующий существующий claim и транспорт. Проверять точный order ID/shop/сумму/модель/срок, не создавать ledger возврата ради обхода маршрута. Отбор должен быть ограничен до LIMIT. До окончания периода — ноль отправок. Возврат, review, чужой shop или отсутствующий зарегистрированный чек предоплаты запрещают отправку.
Тесты: до/на/после границы, чужой заказ, неверная сумма, конфликт с возвратом, повторный и конкурентный запуск, сбой после claim и после HTTP, восстановление без второго POST.

## Итерация 03.2 — расписание
Отдельная миграция закрытой allowlist и ограниченного расписания, выключенного по умолчанию; RLS/запрет API-ролям, подпись короткоживущего запроса по образцу существующего scheduler без токена в pg_net queue. Точный order ID, срок действия допуска и лимит попыток. Расписание останавливается при зарегистрированном чеке, review, истечении допуска или лимите; первый запуск после реального period_end. Не останавливать только по уже выданному доступу. Новые платежи и возвраты расписание не создаёт.

## Итерация 03.3 — подготовка stage
Подготовить preview/provision отдельного короткого тестового периода до оплаты. Длительность и цена фиксируются при создании; даты существующих заказов не меняются. Создать новую изолированную организацию и обычный заказ без trial/возвратов. PR/CI и выпуск требуют отдельного разрешения. В отчёте явно различать технический короткий период и обычную месячную покупку.

## Итерация 03.4 — приёмка
1. Оплата и зарегистрированный чек полной предоплаты; один выданный период.
2. До окончания периода зачёта нет.
3. Реальный запуск расписания после окончания создаёт один чек full_payment с settlements=prepayment на полную сумму, без нового списания.
4. Повторный запуск/перезапуск приводит только к сверке, число операций не растёт.
5. Подтвердить зарегистрированный чек, отсутствие возврата и корректное окончание доступа. Зафиксировать данные запуска cron и серверное состояние, не только UI.
6. Выключить временное расписание и флаги, подтвердить неизменность других заказов.
