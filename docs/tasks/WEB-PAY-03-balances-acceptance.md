# MODEL-03 — сценарий полной sandbox-приёмки

Статус 28.09.2026: план по текущему коду, не разрешение на создание платежа или включение отправки. Схема и функции опубликованы на stage, новые флаги выключены; базовая приёмка выключенного endpoint и чтения старых заказов завершена.

## Выявленные границы продукта

request_platform_subscription_refund (20260925040000) сохраняет один subscription_refund_requests на order_id. Повтор возвращает исходный запрос, а сумма рассчитывается от оставшегося времени на момент первого запроса; после period_end она равна нулю. Клиент не задаёт сумму. Успешный возврат прекращает связанный период однократно (20260925043000). MODEL-03 повторно использует этот контракт, а не создаёт произвольные последовательные возвраты.

Поэтому цепочка старого технического эксперимента ЮKassa с двумя возвратами не является сквозным сценарием текущей админки. Низкоуровневая поддержка refund_after не означает наличие пользовательского сценария компенсации после окончания услуги. Такой сценарий требует отдельного решения о причинах, сумме, разрешениях и доступе.

Новый worker зачёта (20260928015000) выбирает только существующие ledgers после исходного period_end. Частичный возврат не переносит этот срок. Новый ledger создаётся при резервировании связанного возврата; обычный заказ без возврата сохраняет прежний маршрут. Эти границы нельзя скрывать в отчёте о полной приёмке.

## Основной сценарий A: частичный возврат → зачёт остатка

Предлагаемые параметры теста: отдельная sandbox-организация без trial, будущих периодов и запланированной смены тарифа; один новый заказ на 990 ₽, только тестовый магазин/кошелёк, без автопродления. Идентификаторы фиксируются после создания, не подставляются из старых экспериментов. Сумма 990 ₽ — предложение для последующего согласования, платёж пока не создаётся.

1. Preflight: сверить test=true/shop, разрешённую организацию, отсутствие старых операций, модель subscription_access_v1, service/full_prepayment/vat_code=1 и неизменяемые условия периода. Все новые флаги false. Зафиксировать серверное время и ожидаемые границы.
2. Создать и оплатить ровно один новый тестовый заказ после согласования. Подтвердить paid/succeeded, точный платёж, исходный succeeded-чек и однократную выдачу периода. Без подтверждённого чека остановиться.
3. Во время периода получить серверный расчёт через существующий prepare-маршрут. Это фиксирует requested_at и сумму; не использовать кнопку расчёта как безвредный предварительный просмотр перед длительным ожиданием. Для сценария требуется 0 < сумма возврата < 990 ₽, возврат и остаток не меньше 1 ₽; неподходящие значения не исправлять вручную.
4. Для конкретного requestId выполнить reserve/execute нового маршрута при свежем owner/MFA. Проверить одну пару денежных/фискальных резервов, неизменяемые commandId/body/hash/key и ровно один POST. Сумма определяется запросом шага 3, а не заранее заданными 317,43 ₽.
5. Подтвердить деньги succeeded и однократное прекращение периода. До succeeded-чека показывать отдельный неполный фискальный статус. Повтор execute с тем же commandId должен только сверять, без новой отправки или повторного изменения доступа. У провайдера проверить точные refundId и строки чека.
6. До сохранённого period_end заказ не должен попадать в due. После конца периода и подтверждения чека возврата новый worker должен выбрать ровно этот заказ. Старые очереди не должны его выбирать.
7. Выполнить единственный зачёт остатка: full_payment, settlements prepayment, точная сумма 990 ₽ минус успешный возврат; количество из сохранённого журнала. Нового списания нет. Повтор/перезапуск — только GET. Подтвердить succeeded-чек с точным ID.
8. Финальная сверка: исходная сумма = возвращённые деньги + зачтённая сумма; доступ прекращён один раз; нет unresolved/review; заказ вышел из due/reconcile. История отдельно показывает деньги, чек возврата, зачёт и доступ. Выключить новые флаги по завершении согласованного окна, сохранить журнал без контактов/ключей.

## Ускорение без ожидания календарного месяца

Не менять period_start/period_end уже оплаченного заказа, снимок или серверные часы. В текущем публичном checkout нет подтверждённой возможности задать короткий приёмочный период. До ускоренной stage-проверки требуется отдельно разработать ограниченный fixture-механизм, который до оплаты создаёт согласованные order/terms/подтверждение периода для одной тестовой организации и тестового магазина.

Требования к будущей фикстуре: deny-by-default; точные организация/магазин; одноразовый идентификатор и идемпотентность; короткий период (предлагается 30 минут, с возвратом около середины); без production и произвольного клиентского выбора дат; полное совпадение снимков, binding и доступа; запрет изменения после подготовки/оплаты; тесты RLS, повторов и отказов. Окончание периода не должно наступать раньше подтверждения исходного чека и расчёта возврата. При задержке не продлевать заказ вручную, остановить сценарий. Фикстура пока не реализована.

Без этой фикстуры сценарий A выполняется на обычном периоде и ждёт его реального окончания. Локальные SQL-тесты могут проверять границы времени немедленно, но не заменяют сквозную stage-приёмку.

## Остальные сценарии и предел доказательств

- B: полный возврат до начала периода — отдельный заказ, возврат всей суммы, остаток ноль, никакого зачёта. Нужен отдельный разрешённый будущий период; сценарий не совмещается с A.
- C: неизвестный результат/сбой сети/конкурентный retry — существующие имитационные и SQL-тесты. Не провоцировать реальный timeout после POST ЮKassa ради приёмки; в stage проверять безопасный повтор уже известного commandId.
- D: возврат после зачёта — технический адаптер и SQL плюс завершённый отдельный эксперимент ЮKassa. Сквозной административный сценарий пока отсутствует; не обходить ограничения ручными SQL-вставками.
- E: заказ без возврата/без ledger — проверка прежнего маршрута отдельно. Общий переход всех modeled-заказов в MODEL-03 требует отдельного изменения, не включения текущего флага.

## Включение и изоляция

Флаги endpoint и worker действуют на магазин/доступный scope, не на один произвольный orderId. До включения обязательно проверить полный состав due/reconcile и sandbox scope. Если есть другие допустимые операции, сначала подготовить ограничение запуска конкретным заказом; нельзя рассчитывать, что первый элемент очереди — тестовый.

Порядок после готовности фикстуры/изоляции и согласования: краткое окно нового возврата → сверка его результата → отдельное окно GET-сверки → отдельное окно dispatch зачёта после срока. Нельзя считать включение одного frontend-флага достаточным. Не включать legacy-очередь зачёта для нового ledger. Не запускать весь sandbox-reconcile ради одного теста без оценки других фаз worker.

До первого расчёта возврата необходимо выпустить stage-админку с VITE_ADMIN_SUBSCRIPTION_FISCAL_REFUNDS_ENABLED=true; также проверить VITE_ADMIN_SUBSCRIPTION_REFUNDS=true для видимости формы. Первый расчёт сохраняет fiscalMode в sessionStorage; нельзя сначала рассчитывать через legacy и затем менять режим сохранённой операции.

Путь оплаты: приложение stage.qvesta.ru, выбранная организация 28839039-1be3-f3a6-7848-5e31f664d53a. SandboxCheckout.recoverSandboxCheckout восстанавливает подготовленный заказ серверным find_pending_sandbox_order. Не создавать предложение/второй заказ. sandbox-checkout принимает только orderId, проверяет доступ и использует сохранённый receipt даже при RECEIPTS_REQUIRED=false. Его CORS не разрешает stage-admin: оплачивать через приложение, не вызывать его из админки и не извлекать пользовательский JWT. Сверка исходного чека — повтор того же checkout (GET после сохранённой отправки), без общей очереди.

До создания заказа должны быть готовы: фискальная форма возврата, рабочая сессия приложения в нужной организации, проверенный операторский вызов sandbox-subscription-fiscal-order с точным серверным targetOrderId. В существующем deploy-staging reconcile-order вызывает другой endpoint и проверяет только оплату/доступ; он не заменяет изолированный фискальный worker. Операторский запуск последнего ещё требуется оформить/проверить без чтения секретов агентом. Поэтому полный сценарий A пока не готов к запуску.

Предлагаемое согласуемое окно после закрытия предпосылок:
1. Включить только ADMIN_FISCAL_ACCEPTANCE_PREPARE_ENABLED; владелец вводит адрес в stage-форму, подтверждает MFA и создаёт ровно один заказ. Сверить orderId/terms. Сразу выключить подготовку. T0 и T0+30 минут берутся из ответа, не пересчитываются вручную.
2. Через приложение продолжить тот же заказ: ровно один sandbox-платёж 990 ₽ в shop 1467641. Подтвердить test=true, исходный succeeded-чек и однократный доступ. При неопределённом результате только повтор/GET того же заказа; не продлевать период.
3. Около T0+15 минут включить ADMIN_SUBSCRIPTION_REFUNDS_ENABLED и ADMIN_SUBSCRIPTION_FISCAL_REFUNDS_ENABLED для owner/MFA. В фискальном режиме выполнить один серверный расчёт и возврат; сумма и остаток должны быть не меньше 1 ₽, сумма строго меньше 990 ₽. После подтверждения выключить эти флаги. Не вводить сумму вручную.
4. Изолированный worker: YOOKASSA_SANDBOX_FISCAL_ACCEPTANCE_ORDER_ID равен сохранённому заказу; ENABLED=true, DISPATCH=false для GET-сверки возврата. После periodEnd и succeeded-чека возврата отдельно разрешить DISPATCH=true для зачёта остатка. Повтор не должен создавать второй POST. Общие очереди/legacy settlement не включать.
5. Остановка в finally независимо от исхода: PREPARE, оба refund-флага, ACCEPTANCE_ENABLED/DISPATCH=false; общие receipt/settlement/subscription-dispatch остаются false. Существующий глобальный YOOKASSA_SANDBOX_ENABLED=true не выключать без отдельного решения, так как затронет остальные 9 организаций. Сверить деньги=возврат+зачёт и раздельные статусы чека/доступа. Не подтверждённые операции оставить на проверку, не повторять под новыми ID.

В этой итерации изменены только план и отчёт; конфигурация, заказ, платежи и production не менялись. Истечение допуска до готовности требует нового согласованного механизма допуска; ручное продление существующей fixture запрещено её контрактом.
