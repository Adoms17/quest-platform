# Проверка точности quantity в тестовом магазине ЮKassa

Статус: подготовлено, запросы не отправлены. Проверка арифметики не доказывает поддержку формата агентским сервисом. Использовать отдельный синтетический платёж; оплаченный заказ на 24 октября не затрагивать.

## Условия запуска

1. В ЛК выбран именно тестовый магазин stage.qvesta.ru. Проверить доступный сценарий проверки чеков и записать его название. Не заменять агентский сценарий сторонней кассой и не считать их результаты эквивалентными.
2. Перед любым POST серверный GET /me должен подтвердить test=true и ожидаемый shop_id. Перед возвратом GET платежа должен подтвердить test=true, нужного получателя, сумму, валюту и succeeded/paid. Секреты в файл/логи не записывать; .env не читать.
3. Email ниже — заглушка. Для реального тестового запроса использовать согласованный контакт владельца, не произвольного третьего лица. PAYMENT_ID заменить ID отдельного подтверждённого тестового платежа.
4. Для каждой операции сохранить неизменяемые тело и свой Idempotence-Key до POST. Ответ с неизвестным результатом не повторять новым ключом; после 24 часов не повторять и старым ключом без выяснения результата. Сохранить только безопасные статусы, идентификаторы и возвращённые quantity/amount; исключить контакты и заголовки авторизации.
5. Не включать глобальные фискальные флаги stage для одного эксперимента. Действующие builders/SQL блокируют частичные фискальные операции, поэтому пакет ниже нельзя отправлять через них без отдельного тестового инструмента и проверки его границ.

## Исходная позиция

Отдельная тестовая услуга на 990.00 RUB, quantity=1.000, vat_code=1, payment_subject=service, payment_mode=full_prepayment. Сохранить принятый провайдером исходный состав. Дождаться результата чека: один факт успешной оплаты недостаточен для проверки возврата фискальных строк.

## Возврат A: проверяем шесть знаков

```json
{
  "payment_id": "PAYMENT_ID",
  "amount": { "value": "317.43", "currency": "RUB" },
  "receipt": {
    "customer": { "email": "REPLACE_WITH_APPROVED_TEST_EMAIL" },
    "items": [{
      "description": "Тест точности частичного возврата услуги",
      "quantity": "0.320636",
      "amount": { "value": "990.00", "currency": "RUB" },
      "vat_code": 1,
      "payment_subject": "service",
      "payment_mode": "full_prepayment"
    }]
  }
}
```

Название позиции и реквизиты должны совпасть с зафиксированной исходной позицией. Произведение 317.42964 RUB округляется в 317.43. Если сначала округлить quantity до 0.32, получится 316.80; это несовместимый режим. Проверить не только HTTP, но и фактически сохранённое количество, сумму строки и статус чека. При canceled/unknown остановиться; не выполнять следующий возврат по предположению.

## Возврат B: оставшаяся сумма

Только после однозначного успешного A: тело аналогично, amount.value=672.57, items[0].quantity=0.679364, цена единицы остаётся 990.00. Произведение 672.57036 RUB округляется в 672.57; сумма количеств A+B ровно 1.000000. Это второй частичный возврат относительно исходного платежа; receipt не опускать автоматически лишь потому, что денежный остаток станет нулём.

Итог: refunded_amount=990.00, остаток=0, две уникальные операции возврата и два соответствующих результата чеков. Возвраты не смешивать с зачётом в этом эксперименте: цель — изолированно подтвердить точность quantity. Последовательность возврат → зачёт остатка → возврат после зачёта проверяется отдельным платежом после подтверждения арифметики и привязки чеков.

## Отдельные граничные сценарии

- 999.00 с возвратами 317.43 и 672.57: денежный остаток 9.00, не ноль. Количества рассчитываются заново от 999.00.
- 10.00 → 9.00 → 1.00: последний возврат всего остатка в 1 RUB.
- На отдельном платеже с остатком 1.00 запрос возврата 0.50: ожидаемый отказ согласно письму поддержки; не уменьшать обязательство перед клиентом.
- 10.00 → 9.50 и отдельная проверка 0.50: зафиксировать код отказа/принятия, не выводить ограничения только из арифметики.
- Ошибка/тайм-аут POST: сохранить unknown, GET/ЛК и ручной разбор при отсутствии однозначной связи. orderID из письма не считать автоматически уникальным ID чека.

## Критерий решения

Если шесть знаков принимаются и сохраняются, обе суммы и остатки совпадают, а статусы чеков успешны в подтверждённом режиме — это основание для проектирования соответствующего sandbox-контракта с ограниченной точностью. Не распространять результат на произвольные суммы: для максимальных safe integers фиксированной точности недостаточно.

Если quantity округляется до двух знаков или схема отклоняет шесть знаков — сохранить ошибку и направить точные JSON/суммы поддержке; самостоятельно не менять цену единицы и не вводить скрытое округление возврата. Настоящая фискальная регистрация и доставка остаются отдельной приёмкой.
