# PROD-PAY-05 — stage-приёмка защиты без новых платежей

Статус 01.10.2026: план приёмки, НЕ выполненная удалённая проверка. Новый guard/pin остаётся локальным. Настоящие Auth/RPC/браузерные результаты фиксировать только после разрешённого stage-выпуска точного SHA.

## Входные условия

Зафиксировать согласованный SHA, хеши guard/pin, проект jeugfyaqzfgdvfhdxfht, версии опубликованных Edge-функций и UI. Подтвердить остановку отправителей и отсутствие операций в полёте, неактивность cron, выключение всех отправляющих флагов, явное sandbox после guard/pin. Не использовать production, новые заказы, оплату, возврат или отправку чека для доказательства доступности интерфейса. Исторические операции использовать только для чтения. Не сохранять токены/MFA/адреса чеков в артефакты.

## Проверки

| Сценарий | Действие | Ожидаемое доказательство |
|---|---|---|
| Неавторизованный пользователь | Открыть защищённый раздел; запросить читающий ресурс без сессии | Вход/отказ, без приватных данных и provider POST |
| Аккаунт без административных прав | Открыть stage-админку и раздел платежей | Доступ запрещён сервером; одной проверки UI недостаточно |
| Владелец без свежего MFA | Запросить допустимое чтение; проверять запрет команды тестом без реальной операции | Чтение по политике; команда не выдаёт допуск. MFA вводит пользователь, код в чат не передаётся |
| Владелец со свежим MFA | Открыть уже существующую операцию | Статус/чек/возврат читаются по сохранённому ID; новая операция не создаётся |
| Чужая организация или неверный ID | Читающий запрос к заранее согласованной тестовой записи | Нет чужих приватных данных; идентификаторы в отчёте обезличены |
| Отправки выключены | Проверить конфигурацию и поведение выключенного endpoint | Нет POST к провайдеру; не считать сам HTTP 503 достаточным доказательством |
| Повторное открытие и обновление | Загрузить ту же карточку повторно | Тот же ID/статус, без новых заказов, возвратов и dispatch |
| Обновление интерфейса после выпуска | Проверить SHA/версию и загрузку разделов | Тестируется опубликованная версия, а не старый кэш |

SQL-отказы production/unconfigured на уже сохранённой операции проверяются в изолированной БД. Не переключать stage в production ради приёмки: закрепление среды и остановка отправителей имеют отдельный порядок. Для проверки настоящего сетевого отрицательного пути нужны специально подготовленные безвредные сценарии с утверждённой записью и доказанно выключенной отправкой; не вызывать платёжные команды наугад.

## Отчёт приёмки

Для каждого сценария сохранить дату, SHA, среду, роль (без учётных данных), действие, HTTP-код/безопасный код ошибки, результат и свидетельство отсутствия побочного эффекта. Недоступную проверку отметить NOT RUN с причиной. Отсутствие секретов в ответе и отсутствие provider POST проверяются отдельно. Этот документ пока не содержит PASS удалённой приёмки.

## Локальные доказательства

На 01.10.2026 прошли 100 тестов восьми наборов: sandboxRefundIdentity, sandboxRefundHandler, sandboxRefundGateway, subscriptionRefundPreparationEndpoint, subscriptionRefundEndpoint, subscriptionFiscalRefundEndpoint, fiscalAcceptanceEndpoint, platformRefundEndpoint. Они проверяют подпись через контракт getClaims, getUser, совпадение sub, authenticated/aal2, exp, свежий TOTP, payload и gateway-авторизацию с синтетическими зависимостями. Это не проверка реального SDK/Auth по сети.

Фискальный refund endpoint повторно вызывает Auth перед отправкой; обычный refund endpoint повторно проверяет через SQL recover сохранённый identity/MFA/expiry. Не приравнивать эти механизмы к одинаковой проверке отзыва Auth-сессии в момент POST. Этот аспект нужно явно учесть в production-контракте, не выводить из успешных mock-тестов.
