## Последовательность после разрешения

1. Commit/push и PR в staging. Проверить CI на точном SHA. Слияние и публикация — отдельные действия, не разрешённые самим PR.
2. После разрешённого слияния запустить workflow Deploy Supabase staging с operation=subscription-model-dry-run на staging. Убедиться, что pending содержит только три manifest-миграции (либо последовательный остаток). Операция dry-run не меняет флаги.
3. После разрешения применения запустить subscription-model-apply. Workflow привязан к github.sha, environment staging и точному project id; выключает четыре rollout-флага, повторно проверяет историю/dry-run, применяет схему, проверяет отсутствие pending.
4. Запустить разрешённую subscription-model-functions-deploy на том же проверенном staging SHA. Требует полностью применённой схемы и повторно выключает четыре флага; публикует только sandbox-reconcile.
5. Проверить журнал успешного отключения флагов, версии функции и браузерное чтение старых платежей/чеков. Не создавать активную model-политику и не включать флаги в рамках этого выпуска. Фискальная и денежная приёмка отдельные.

Флаги, каждый false: YOOKASSA_SANDBOX_RECEIPTS_REQUIRED, YOOKASSA_SANDBOX_RECEIPT_RECONCILIATION, YOOKASSA_SANDBOX_SETTLEMENT_RECONCILIATION, YOOKASSA_SANDBOX_SETTLEMENT_DISPATCH.

## Остановка и восстановление

При неуспехе любой проверки не применять вручную пропущенные команды. Сохранить лог/SHA. При частичной миграции повторить проверку manifest/history; не менять уже применённый SQL, не удалять fiscal-таблицы и историю. При сбое функции держать четыре флага выключенными; прежняя функция совместима с аддитивными таблицами. Отдельно согласованный откат функции не означает откат БД или исправление unknown-платежей.

Ожидаются технические ответы ЮKassa и проверка момента зачёта ФНС. Этот выпуск не включает реальную фискализацию и production.
