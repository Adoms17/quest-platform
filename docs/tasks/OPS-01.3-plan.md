## План

1. **Просмотр sandbox-платежей и возвратов.** Новое отдельное право чтения владельцу и продажам в области назначения. Серверный RPC с проверкой MFA/активности роли/организации, закрытым аудитом и курсорной пагинацией (25 записей). Экран в карточке организации через общий api layer. Другие роли пока не получают расширенные финансовые данные: матрица требует отдельных ограниченных проекций/оснований обращения.
2. **Предварительный расчёт возврата.** Владелец и продажи могут получить серверный расчёт полной/частичной суммы; просмотр не резервирует деньги и не отправляет запрос провайдеру. Явно показывать, что доступ сохраняется. Учитывать выполненные, ожидающие и требующие проверки возвраты; не рассчитывать доступный остаток только в браузере.
3. **Подтверждение и исполнение владельцем.** Отдельная проверка свежего MFA, области и полномочия; причина, подтверждённые параметры, повторная серверная проверка суммы, command_id и аудит. Действующие service_role функции остаются закрытыми для браузера. Проработать переход от operator allowlist без неявного расширения прав и без обходного старого пути.
4. **Восстановление и сверка.** Повтор команды без второго возврата; timeout/неопределённость не означают отказ; подтверждение результата провайдером. Отзыв роли действует и для retry. Не менять доступ, квоты и историю прохождений.
5. **Проверки и выпуск.** SQL/RLS на изолированной базе, браузерные проверки с синтетическим API, настоящий Auth/MFA, затем отдельно разрешённые commit/PR/merge/stage. Реальные денежные операции и production не входят в текущую реализацию.

## Контракт первого среза

Только sandbox, явная маркировка. Возвращать разрешённую проекцию: ID заказа/платежа, даты, сумма в копейках и валюта, состояние оплаты, признак проверки, агрегаты возвратов. Не отдавать shop_id, confirmation_url, ключи идемпотентности, actor_id, сырые ответы провайдера и платёжные реквизиты. 100%-скидка без платежа не должна изображаться оплаченной денежной операцией: в первом списке только записи sandbox orders; нулевые заказы отдельно обозначить как будущую проекцию заказов.

Критерии: отказ без MFA, после отзыва/истечения назначения и для чужой организации/курсора; прямой доступ к таблицам запрещён; отсутствие лишних полей; корректная пагинация при одинаковых датах; изоляция тестовых данных от существующих записей; ошибки и пустой список в UI; защита от показа результата предыдущей организации после переключения.

## Авторизация исполнения подтверждённых возвратов

Миграция 20260922040000_authorize_platform_refund_execution.sql связывает существующие read_sandbox_refund / begin_sandbox_refund с platform_refund_commands. Для возвратов админки требуется действующий owner и свежий MFA; operator allowlist не является альтернативой. Для старых возвратов прежний операторский механизм сохранён. Функции остаются доступны только service_role, не authenticated. Вызывающий сервер должен передавать проверенную личность владельца: один service JWT без пользовательского контекста недостаточен.

Перед началом проверяются соответствие команды резерву, организация, sandbox scope, подтверждённый платёж и отсутствие payment review. Удержанная сумма не резервируется повторно. Запись/отклонение результата используют существующий read_sandbox_refund и поэтому также проверяют владельца. Если права отозваны после запроса провайдеру, сохранение через ручной путь может быть запрещено: резерв не освобождать, результат восстанавливать через доверенную сверку.

Это ещё не endpoint отправки. База не может атомарно связать отзыв роли с внешним HTTP-запросом; будущий endpoint должен проверять полномочия непосредственно перед POST и явно учитывать операцию, уже принятую провайдером. Фоновая сверка результатов не должна создавать новый возврат.
Проверки: SQL replay 51 миграции успешен; проверены серверный begin без operator allowlist, запрет браузеру, свежий MFA на повторе и невозможность обойти отзыв владельца через operator allowlist. Lint/build/git diff --check успешны с прежними предупреждениями. Общая локальная база, stage, production и провайдер не изменены; commit/push/deploy не выполнялись.
