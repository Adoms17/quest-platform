# WEB-PAY-03 — подготовка выпуска чеков на stage

Статус 27.09.2026: локальный пакет, не применён на stage. Подключение «Чеков от ЮKassa» и ответы поддержки остаются условиями фискальной приёмки.

## Состав и проверка

`WEB-PAY-03-migrations.json` фиксирует 19 миграций 20260926019000–20260926037000 и SHA-256 текста SQL после удаления BOM и нормализации CRLF в LF. Миграция цен 20260926038000 в пакет не входит: она выпущена отдельно.

Проверка `scripts/check-receipt-stage-release.mjs` принимает сохранённый вывод истории миграций, сверяет файлы и допускает только незавершённые миграции пакета. Чужая ожидающая миграция, расхождение remote/local, дубликат или отсутствие элемента пакета останавливают выпуск. Повторное применение допускает частично завершённый пакет. `--require-applied` проверяет отсутствие ожидающих миграций.

Пакет перенесён на актуальную staging (см. отчёт ниже); существующий workflow публичных тарифов сохранён. Перед применением проверить зависимости от ранее выпущенных документов покупки и возвратов по фактической истории stage.

## Порядок выпуска

1. Прогнать тесты guard, чеков и полный replay схемы в отдельной временной БД; затем lint/build. Для replay используется `QVESTA_TEST_CHECKOUT_DOCUMENTS=1` и `npm test -- scripts/checkout-documents-integration.test.js`. Он читает только схему Auth локальной БД и выполняет изменения в отдельном тестовом контейнере.
2. Получить свежую историю миграций stage. При `SUPABASE_PROJECT_ID=jeugfyaqzfgdvfhdxfht` запустить `node scripts/check-receipt-stage-release.mjs <файл-истории>`.
3. Использовать операции существующего workflow `deploy-staging.yml`: `receipts-dry-run` и `receipts-apply`, только ветка staging. Он разделяет общий замок `supabase-staging` с существующими выпусками. Номер уже применённой миграции тарифов выше пакета чеков: нельзя автоматически применять все старые миграции через `--include-all`. Сначала guard, затем dry-run; список dry-run должен совпасть с ожидающим подмножеством manifest.
4. Применить проверенный пакет и снова проверить историю с `--require-applied`. Затем выпустить совместимые Edge Functions и интерфейсы. Зафиксировать SHA, результат миграций и версии функций.
5. На первом выпуске оставить выключенными `YOOKASSA_SANDBOX_RECEIPTS_REQUIRED`, `YOOKASSA_SANDBOX_RECEIPT_RECONCILIATION`, `YOOKASSA_SANDBOX_SETTLEMENT_RECONCILIATION`. Не отключать действующую базовую сверку платежей. Не создавать фискальную политику с предположительными параметрами.
6. Проверить прежнюю sandbox-покупку и чтение административной карточки, права доступа и отсутствие новых фискальных отправок. При ошибке остановить выпуск; не удалять записи чеков и не откатывать БД разрушительными миграциями.

## После ответа ЮKassa

Уточнить поддерживаемый тестовый магазин, параметры АУСН/«Без НДС», предмет расчёта, момент зачёта предоплаты, строки частичного возврата и обязательные поля покупателя. Затем создать подтверждённую sandbox-политику с MFA и провести отдельную приёмку ручной покупки, продления, полного возврата и восстановления неизвестного результата.

Неизвестный результат отправки проверять чтением существующей операции, без повторной отправки. Проверить изоляцию магазинов, неизменность запроса и отсутствие второго чека при повторном запуске. Автоматическое создание зачёта и частичные возвраты остаются незавершёнными; GET-сверка не заменяет их. Production в этот выпуск не входит.
