# Резервное копирование — подготовка до коммерческого запуска

## Состояние на 24.09.2026

Реализован и выполнен только синтетический проверочный цикл. Это не резервная копия stage/production и не подтверждение полного восстановления Supabase. Реальные данные не выгружались, Google Диск не подключён, расписание копирования не включено.

## Проверочный запуск

Из корня рабочей копии:

```powershell
npm.cmd test -- scripts/backup-crypto.test.js --maxWorkers=1
node scripts/backup-restore-drill.mjs --synthetic
```

Требуется Docker с образом supabase/postgres:17.6.1.165. Команда не принимает адрес рабочей базы. Создаётся отдельный контейнер без сети и опубликованных портов, две отдельные базы с синтетическими записями, первичным ключом и tenant RLS. pg_dump custom-format шифруется AES-256-GCM, записывается в системную временную папку и копируется во второй файл, имитирующий перенос. Это локальная копия, не облачная проверка. После сравнения SHA-256 и успешной аутентификации архив подаётся pg_restore. Сравниваются все синтетические строки, первичный ключ и видимость строк для ограниченной роли.

Ключ создаётся случайно в памяти на один запуск; не печатается и не сохраняется. Временные файлы и собственный контейнер удаляются в finally. Архив этого теста не предназначен для последующего использования. Общая локальная Supabase не используется даже как источник данных. Роль для восстановления создаётся отдельно в тестовом контейнере; dump базы не заменяет резервирование глобальных ролей.

## Формат прототипа

scripts/backup-crypto.mjs: заголовок QVESTA-BACKUP-1, случайный nonce 12 байт, тег GCM 16 байт, шифротекст. Заголовок аутентифицируется как AAD. Ключ — 32 случайных байта, не пароль. Расшифрованные данные возвращаются вызывающему коду только после проверки тега. Отвергаются неверный ключ, повреждение заголовка/тега/данных, обрезание и приписанные байты. SHA-256 обнаруживает повреждение переноса; защиту от подмены обеспечивает GCM.

Ограничение прототипа: до 64 MiB данных в памяти. Он не предназначен для больших production-дампов. Права 0600 применимы на поддерживающей их системе; на Windows они не заменяют проверку NTFS ACL и шифрование диска. Никаких гарантий безопасного удаления на SSD не заявляется.

## Целевая схема реальных копий

1. Приватная рабочая папка вне Git и облачной синхронизации. До выгрузки проверить ACL, доступное место и шифрование локального диска.
2. Постоянный ключ с отдельной резервной копией хранится вне каталога архивов — в согласованном менеджере секретов или на отдельном защищённом носителе. Значение ключа не передаётся в чат, исходники, аргументы CLI и логи. Сначала проверить восстановление ключа.
3. Снимать согласованный комплект: роли, схема, данные, история миграций; отдельный экспорт файлов Storage с манифестом и хешами. Для реального Supabase использовать поддерживаемый CLI-процесс, а не слепо переносить pg_dump из синтетического теста. Учитывать Auth, RLS, пользовательские функции/триггеры и внешние зависимости.
4. Только завершённые зашифрованные архивы с безопасным манифестом помещать в отдельную папку Google Диска. Ключ и открытые дампы туда не помещать. Проверка существования файла в папке синхронизации не доказывает загрузку в облако: нужна независимая загрузка обратно и сверка хеша.
5. После успешного пробного восстановления согласовать расписание, сроки хранения и уведомления об ошибках. Предложение для обсуждения: ежедневно, 7 ежедневных + 4 еженедельных + 3 месячных копии. Автоматическое удаление пока не реализовано и не включено.
6. Регулярно восстанавливать независимо скачанный архив в изолированную среду и проверять таблицы, ограничения, RLS, Auth и доступность файлов Storage. Измерять фактические RPO/RTO, не объявлять их по расписанию без измерений.

Vault требует отдельного плана восстановления ключевого материала и секретов: наличие зашифрованных строк Vault в дампе само по себе не доказывает возможность их расшифровать в новом проекте. Worker-токены, конфигурация Auth, Edge secrets, DNS и Cloudflare также не считаются автоматически восстановленными из дампа БД. Секреты не извлекать для документации.

## Выбранное хранение ключа: Kaspersky Password Manager

Алексей использует Kaspersky Password Manager. Google Диск доступен через браузер, без Desktop: первый перенос архивов будет ручным. Алексей подтвердил создание и сохранение постоянного ключа; автоматическое получение ключа из KPM не настроено и не предполагается.

Создать в KPM заметку «Квеста — резервные копии — ключ 01». Указать назначение AES-256-GCM, формат ключа Base64 (32 случайных байта), дату создания и идентификатор key-01. Не использовать пароль от KPM как ключ архива. Локальный ввод принимает канонический Base64 с проверкой ровно 32 декодированных байт; ключ передаётся в Node через stdin, не через аргументы или переменные окружения.

Для создания ключа самостоятельно на Windows сначала отключить журнал буфера обмена и его синхронизацию между устройствами. Открыть локальный PowerShell и выполнить команды ниже. Значение не печатается в терминал и не входит в историю команд; в истории остаётся только код генерации. Пока ключ в буфере, вставить его в заметку KPM, сохранить, повторно открыть заметку и проверить наличие значения. Не присылать заметку, ключ или скриншот в чат. После сохранения вернуться в PowerShell и нажать Enter для очистки буфера.

```powershell
$backupKeyBytes = New-Object byte[] 32
$backupKeyRng = [Security.Cryptography.RandomNumberGenerator]::Create()
try {
    $backupKeyRng.GetBytes($backupKeyBytes)
    Set-Clipboard -Value ([Convert]::ToBase64String($backupKeyBytes))
} finally {
    $backupKeyRng.Dispose()
    [Array]::Clear($backupKeyBytes, 0, $backupKeyBytes.Length)
    Remove-Variable backupKeyBytes, backupKeyRng
}
Read-Host 'Вставьте ключ в заметку KPM, сохраните её, затем нажмите Enter' | Out-Null
Set-Clipboard -Value ' '
```

Это действие выполняет владелец локально. Ассистент не запускал генерацию и не получал ключ. До первого реального архива нужно проверить восстановление с сохранённым ключом, согласовать защищённую рабочую папку и восстановление доступа к самому KPM. Старый ключ сохранять, пока существуют зашифрованные им архивы; замена записи новым ключом лишит доступа к старым копиям.

Официальная инструкция KPM по добавлению записей: https://support.kaspersky.com/help/kpm/win10.3/en-US/85106.htm

## Проверка переноса через Google Диск

Алексей подтвердил успешный локальный тест с ключом из KPM. Добавлены режимы ExportArchive и VerifyArchive. Экспорт сохраняет только зашифрованный архив после успешного локального восстановления; путь должен находиться вне репозитория, файл не перезаписывается. Импорт требует отдельную скачанную копию и исходный архив для SHA-256, проверяет размер, хеш и GCM до pg_restore. Восстановление выполняется в отдельном контейнере без сети. Сам факт облачной загрузки проверочный скрипт не удостоверяет — перенос выполняет владелец в браузере.

Создать архив (Docker Desktop включён, ключ вводится дважды):

```powershell
$backupTool = 'M:\Dev\Projects\quest-platform\tariff-release.local\scripts\Test-BackupSavedKey.ps1'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $backupTool -ExportArchive "$env:USERPROFILE\Downloads\qvesta-test-key01.qvb"
```

Загрузить только qvesta-test-key01.qvb на Google Диск, затем скачать обратно. Скачанную копию сохранить отдельно под именем qvesta-test-key01-downloaded.qvb в Загрузках. Исходный файл сохранить для сравнения. Ключ остаётся в KPM.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File $backupTool -VerifyArchive "$env:USERPROFILE\Downloads\qvesta-test-key01-downloaded.qvb" -ReferenceArchive "$env:USERPROFILE\Downloads\qvesta-test-key01.qvb"
```

Успех импорта: downloadedArchiveVerified=true и «Скачанный архив совпадает с исходным и успешно восстановлен». Это проверка синтетического дампа, не реальных данных и не всех сервисов Supabase.

## Потоковое шифрование — 24.09.2026

Алексей сообщил, что M:, вероятно, не зашифрован. Открытые дампы на этот том не сохраняем. Новый scripts/backup-stream.mjs принимает поток и пишет только шифротекст в исключительно созданный файл; сохраняет совместимость с QVESTA-BACKUP-1. Тег записывается после успешного завершения потока, выполняется sync. Существующий файл не перезаписывается; при обработанной ошибке собственный незавершённый файл удаляется. После аварийного завершения процесса может остаться неполный зашифрованный файл: наличие файла само по себе не означает готовность копии.

Ограничение памяти 64 MiB снято для нового модуля. Сохраняется предел AES-GCM на одно сообщение: 2^36−32 байта. Проверка файла читает его потоком, проверяет GCM, уничтожает получаемые открытые чанки и не передаёт их процессу восстановления. Успех проверки не разрешает повторно открыть изменяемый файл и восстанавливать его без защиты от подмены. Полный безопасный путь восстановления ещё не реализован.

Проверено: 20 тестов PASS (потоковый модуль, прежний формат, ввод ключей), включая 70 MiB, пустой поток, двоичную совместимость, запрет перезаписи, очистку после ошибки источника, неверный ключ, повреждение заголовка/тега/шифротекста, обрезание и приписанные байты. Использовались только синтетические данные и ключи. Синтетический цикл теперь использует потоковую связку процесса pg_dump и шифрования; его восстановление пока сохраняет прежний ограниченный буфер до 64 MiB.

Уточнение защиты: отсутствие открытых временных файлов не исключает попадания памяти в pagefile, hibernation или crash dump на незашифрованном хосте. Docker tmpfs также не даёт безусловной гарантии отсутствия swap у виртуальной машины. До реальной выгрузки/восстановления требуется проверенная среда с защитой этих носителей; не менять системные настройки автоматически. Пока реализован только модуль, stage не выгружался. Следующий шаг — защищённая среда исполнения и подключение производителя дампа с проверкой exit code до признания архива завершённым.
## Завершение экспортёра и публикация архива — 24.09.2026

Добавлен scripts/backup-process.mjs: stdout доверенного процесса поступает прямо в шифрование, stderr не журналируется, shell не используется. Окончание stdout не считается успехом: обязательно дождаться успешного exit code. При ненулевом коде, ошибке запуска или тайм-ауте итоговый файл не публикуется. Тайм-аут завершает непосредственный дочерний процесс; внешние ресурсы, например контейнер, должен очищать вызывающий код. Аргументы не должны содержать секреты.

Архив создаётся с уникальным суффиксом .partial, проверяется GCM, затем публикуется hard link без перезаписи существующего пути. При отсутствии поддержки hard link операция завершается ошибкой. При штатной обработке временный файл удаляется; аварийное завершение может оставить зашифрованный .partial. Папка должна быть защищена от записи посторонними: модуль не является защитой от локального администратора или подмены файла другим процессом с теми же правами.

Синтетический backup-restore-drill переведён на новую связку с настоящим docker exec pg_dump. Контейнер по-прежнему собственный, без сети и портов; finally удаляет только его.
