# MODEL-03 — пакет PR и порядок выпуска

28.09.2026. Ветка codex/subscription-fiscal-balances; база staging dbf566a95fdc0ef3ee54f8f3ad846582ab3eb67b. Пакет локальный, публикация не выполнена.

## Предлагаемый PR

Название: Add isolated subscription fiscal ledger, refunds and settlement reconciliation

Описание:

При частичном возврате подписки последующий зачёт должен учитывать оставшуюся предоплату и ранее подтверждённые чеки. Добавлен закрытый фискальный журнал с точными суммами/quantity, атомарной связью денежного возврата и доступа, однократной отправкой и восстановлением через GET. Административный маршрут повторно проверяет JWT, owner/MFA и состояние заказа непосредственно перед отправкой. UI отдельно показывает деньги, чек и доступ; worker отправляет только зачёт и сверяет возвраты.

Семь аддитивных миграций, серверный маршрут и новая очередь закрыты отдельными выключенными флагами. Заказы нового журнала исключаются из старых очередей. Заказы без ledger сохраняют прежний путь; автоматического импорта старых возвратов/зачётов нет. Это ограниченный совместимый выпуск, не включение MODEL-03 для всех заказов.

Проверено локально: SQL/RLS на полной схеме 318 миграций, конкурентные операции и прежние регрессии; 49 тестов последнего worker/history-среза, три Edge Runtime проверки; 20 тестов manifest/защиты выпуска; новый браузерный сценарий desktop/mobile (2 PASS, 20.2 s); lint и сборки приложения/admin. Точные результаты предыдущих срезов — WEB-PAY-03-fiscal-balances.md. Проверки провайдера используют синтетический fetch; новый end-to-end stage-сценарий ещё предстоит. CI GitHub для этого пакета ещё не запускался.

## Результат локального ревью

- Отправка требует серверного флага; frontend-флаг не является разрешением. Повторный запрос использует сохранённый commandId и не создаёт новый POST.
- Новые таблицы закрыты RLS/revoke; наружу выдаются ограниченные RPC с проверкой владельца/MFA либо service worker с shop/scope.
- Manifest фиксирует семь файлов и SHA-256 с нормализацией CRLF. Проверяются ранее выпущенные manifests и применённые MODEL-01/02. Посторонняя pending-миграция, пропуск, несовпадение remote и применение не по порядку останавливают выпуск.
- Граница покрытия: ledger создаётся при первой новой операции. Worker не захватывает все modeled-заказы без ledger; они остаются в прежней очереди. Перед общим включением нужен отдельный переход для заказов без предыдущих операций и явная стратегия для заказов с историческими возвратами/зачётом. До этого нельзя объявлять MODEL-03 полностью включённым.
- Полносхемный checkout integration включается локально QVESTA_TEST_CHECKOUT_DOCUMENTS=1 и использует schema-only Auth из локального Supabase. Обычный npm test в CI его пропускает; локальный результат не подменяет отдельную SQL-приёмку stage. Новая UI-ветка теперь явно включена отдельным шагом Admin CI.

## Порядок разрешённого выпуска

1. После разрешения владельца: commit/push и PR в staging. Проверить CI, Admin CI и CodeQL для точного head; зафиксировать SHA. Merge и deployment согласовать отдельно.
2. На слитом SHA выполнить subscription-balances-dry-run в deploy-staging.yml. Ожидаются только неприменённые файлы WEB-PAY-03-balances-migrations.json. При ошибке не запускать общий db push в обход guard.
3. Выполнить subscription-balances-apply. Workflow выключает прежние флаги чеков/зачёта и три новых server-флага, повторно проверяет историю/preview, применяет только разрешённый pending-набор и требует пустой остаток. Операция не выпускает функции и не создаёт политику.
4. Выполнить subscription-balances-functions-deploy. Требует применённую схему и совпадающие hashes; повторно выключает флаги; выпускает sandbox-reconcile и admin-subscription-fiscal-refund. Worker сам по себе не запускается. Повтор workflow снова выключает флаги.
5. Админку собрать/опубликовать отдельным штатным процессом, явно задав VITE_ADMIN_SUBSCRIPTION_FISCAL_REFUNDS_ENABLED=false. Этот workflow frontend не публикует. Не использовать тестовую Playwright-сборку как release artifact. Старые UI-флаги сохранять по согласованной конфигурации.
6. Выполнить приёмку ниже с выключенными новыми флагами. Включение GET-сверки, нового возврата и отправки зачёта — отдельные действия после согласования; в пакет нет workflow автоматического включения.

Новые server-флаги: ADMIN_SUBSCRIPTION_FISCAL_REFUNDS_ENABLED, YOOKASSA_SANDBOX_SUBSCRIPTION_FISCAL_RECONCILIATION, YOOKASSA_SANDBOX_SUBSCRIPTION_FISCAL_DISPATCH. Dispatch без reconciliation не активирует очередь. Существующий YOOKASSA_SANDBOX_ENABLED остаётся дополнительным условием. Приёмка формы расчёта требует существующих флагов admin-subscription-refund-prepare.
