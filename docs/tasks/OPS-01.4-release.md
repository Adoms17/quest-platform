## Порядок выпуска с выключенным функционалом

1. Проверить diff и состав коммита; зафиксировать SHA кандидата, CI и историю stage. Не применять все локальные миграции без точного allowlist.
2. Использовать зарегистрированный workflow deploy-staging.yml: сначала operation=recurring-dry-run, затем operation=recurring-apply на том же проверенном SHA ветки staging. Workflow проверяет allowlist до dry-run и повторно перед apply, после apply требует пустой pending-набор. Существующий payments-release по-прежнему отклоняет recurring-миграции. Отдельный recurring-staging.yml недоступен для dispatch без регистрации в default branch; тот же изолированный job перенесён в deploy-staging.yml. Миграции ещё не запускались.
3. Применить миграции штатным Git-процессом после dry-run. Флаги UI/автопродления остаются выключенными, расписание отсутствует.
4. Опубликовать перечисленные функции и frontend того же SHA. Проверить 401 без токена и 503 при выключенном recurring.
5. Только после закрытия условий ниже включить тестовый интерфейс согласия и провести приёмку на отдельной sandbox-организации. Запуск recurring вручную ограниченным worker-вызовом, без расписания.

## Подготовка реальной sandbox-приёмки — 23.09.2026

По коду runSandboxRecurringBatch обработчик вызывает prepare_due_sandbox_recurring(shop), затем list_sandbox_recurring_work(shop). Обе операции ограничены магазином и пачкой до 10, но не одной выбранной организацией. До ручного запуска приёмки требуется серверное ограничение организации одновременно в подготовке и выборе очереди. Фильтрация после чтения очереди недостаточна: подготовка/резервирование уже могли затронуть другие организации.

План следующего среза:
1. Алексей выбрал отдельную тестовую организацию. Подготовить её для приёмки; smoke-organizer не использовать.
2. Добавить отдельную миграцию с безопасным ограничением подготовки/очереди, передаваемым из серверной настройки, не из произвольного тела HTTP. Невалидная настройка должна блокировать работу. Проверить две организации одного магазина: невыбранная не получает заказов, резервов или изменений расписания сверки.
3. Выпустить это ограничение с выключенным флагом и повторить disabled smoke.
4. Включить интерфейс согласия; владелец выбранной организации лично сохраняет v2-согласие и проводит новый checkout тестовой картой. Старые заказы без согласия не преобразовывать в подписку задним числом.
5. Проверить подтверждённое сохранение метода, затем ограниченный ручной запуск без расписания. Отдельно: успешное продление, скидка 50/100%, отзыв, отказ с уведомлением, ручная оплата и повторная сверка без дубликатов. Не сокращать реальные оплаченные периоды/данные организации ради теста; при необходимости подготовить отдельную синтетическую организацию и согласованный тестовый период.
6. После приёмки вернуть recurring=false; записать агрегированные результаты без идентификаторов метода, токенов или платёжных реквизитов.

В этом шаге новые списания и изменения базы не выполнялись; выбрана отдельная тестовая организация, создание ещё не выполнено.
