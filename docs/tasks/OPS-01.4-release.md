# OPS-01.4 — подготовка выпуска на stage

Дата: 23.09.2026. Статус: локальный кандидат, не опубликован. Production вне области выпуска.

## Состав

17 новых миграций: 20260922100000–20260922230000 (почасовые), 20260922233000, 20260922234500, 20260922235000. Требуется полностью применённое основание OPS-01.3 до 20260922090000 включительно. Проверка истории: scripts/check-admin-stage-migrations.mjs --recurring-release; она только проверяет список и не применяет миграции. Существующие режимы платежного/тарифного выпуска не расширены.

Функции: sandbox-checkout, sandbox-reconcile, yookassa-sandbox-webhook получают обновлённые общие модули; новая sandbox-recurring выполняет подготовку, сверку и выдачу. Frontend включает отдельный блок согласия только при VITE_SANDBOX_RECURRING_SETUP=true. Новая функция требует одновременно YOOKASSA_SANDBOX_ENABLED=true и YOOKASSA_SANDBOX_RECURRING_ENABLED=true, а также серверный worker-токен. Значения секретов не помещать в отчёт или Git.

## Порядок выпуска с выключенным функционалом

1. Проверить diff и состав коммита; зафиксировать SHA кандидата, CI и историю stage. Не применять все локальные миграции без точного allowlist.
2. Использовать зарегистрированный workflow deploy-staging.yml: сначала operation=recurring-dry-run, затем operation=recurring-apply на том же проверенном SHA ветки staging. Workflow проверяет allowlist до dry-run и повторно перед apply, после apply требует пустой pending-набор. Существующий payments-release по-прежнему отклоняет recurring-миграции. Отдельный recurring-staging.yml недоступен для dispatch без регистрации в default branch; тот же изолированный job перенесён в deploy-staging.yml. Миграции ещё не запускались.
3. Применить миграции штатным Git-процессом после dry-run. Флаги UI/автопродления остаются выключенными, расписание отсутствует.
4. Опубликовать перечисленные функции и frontend того же SHA. Проверить 401 без токена и 503 при выключенном recurring.
5. Только после закрытия условий ниже включить тестовый интерфейс согласия и провести приёмку на отдельной sandbox-организации. Запуск recurring вручную ограниченным worker-вызовом, без расписания.

## Условия до включения

- Уточнить политику после окончательного отказа. Предложены уведомление и ручная оплата; это ещё не утверждённое решение. Закрытый заказ не возобновляется автоматически.
- Текст согласия и статусы обновлены локально: sandbox-recurring-v2 явно разрешает сохранение метода и тестовые списания. Сервер отклоняет v1. Визуальная проверка отдельного компонента с синтетическим API на 390/1280 px пройдена; нужны интеграционная приёмка checkout и новое явное согласие в sandbox; сохранение согласия не означает включённого серверного флага. Изменена ещё не опубликованная foundation-миграция; если обнаружится среда с применённой прежней редакцией, остановить выпуск и подготовить отдельную миграцию перехода.
- Добавить безопасное уведомление о неудачном продлении и понятный способ ручной оплаты, если эта политика будет выбрана.
- Реальный sandbox: сохранение метода через тестовый checkout; сверка метода; продление, скидки 50%/100%, отзыв до отправки, отказ, восстановление после сбоя, отсутствие повторного периода. Не подменять это результатами синтетического провайдера.
- Проверить сохранение отсутствия доступа к методу оплаты в браузере, RLS/MFA и поведение после окончания поддержки версии.

## Отключение и восстановление

При ошибке выключить YOOKASSA_SANDBOX_RECURRING_ENABLED и UI-флаг, остановить расписание, если оно появится. Это прекращает новые вызовы, но не отменяет уже разрешённые/отправленные платежи. Сохранить журналы и резервы; завершить их сверку отдельным контролируемым действием. Не удалять таблицы, не откатывать миграции с данными, не возобновлять закрытые заказы и не создавать новый idempotency key для неизвестного платежа.
