# PROD-PAY-05 — локальный план миграционного пакета

01.10.2026. Ветка `codex/production-billing-package-plan`, база `07b7395a9e6a831ede0f21f6d4519d377a5224d4` (staging после PR #148–#150). Это подготовка состава для ревью, не исполнимый manifest выпуска.

## Что сделано

`scripts/plan-production-billing-package.js` проверяет зафиксированный candidate manifest и строит JSON с полным списком ожидаемых применённых миграций, ожидающих исторических миграций и двумя SQL-кандидатами в порядке guard → pin. Каждый файл имеет SHA-256 после нормализации CRLF в LF. Исходный проверяющий скрипт используется как общая функция; его команда в CI сохранена.

Проверка также фиксирует границу baseline, порядок инициализации и требование остановленных workers. Неизвестная, изменённая или дублирующаяся локальная миграция останавливает построение. Удалённые подключения, SQL, секреты и запуск процессов выпуска в инструменте отсутствуют.

Из корня этой рабочей копии:

```powershell
node scripts/plan-production-billing-package.js
node scripts/plan-production-billing-package.js --history C:/path/to/production-history.json
```

Первая команда строит локальный план с `historyEvidence: not-supplied`. Второй нужен JSON вида `{ "projectRef": "szjiwamevblkpjmmeonf", "versions": ["..."] }`, где versions содержит **полную** выгрузку версий из read-only запроса `scripts/inspect-production-billing-schema.sql`. Версии — строки из 14 цифр, без сокращений и дублей. Пример многоточия не является допустимым входом. Входной порядок не важен; набор должен точно совпадать с локальной историей до baseline включительно. Любое продвижение production требует нового ревью baseline, а не автоматического пропуска файлов.

JSON передаётся локально; инструмент не подтверждает его происхождение и свежесть. Даже совпадающий список версий не доказывает совпадение содержимого удалённых миграций. Поэтому результат всегда `review-only-not-deployable`, `remoteContentsVerified: false`, с явными оставшимися условиями выпуска. План без history не выдавать за свежую сверку production.

### 1. Завершить локальное ревью и выделить пакет защиты

Остаток аудита 05.1: финальные определения динамически переопределяемых RPC, административные пути/ACL, типы/event trigger bodies/публикации и API exposure, зависимости auth/storage. Проверенные callback и пути применения доступа перечислены в [отчёте](PROD-PAY-05-isolation.md); повторять их без новых изменений не нужно. Отдельно проверить состав локального diff: инструменты сравнения, read-only SQL и снимки; уточнение локального bootstrap; два исправления sandbox guard; регрессии; документы. Исторические 324 миграции не переписывать.

Результат: локально готовый состав ревью с явными ограничениями. Commit/push/PR выполнять только при разрешении владельца; создание PR не означает разрешения на merge/deploy.

### 2. Подготовить и проверить stage-совместимость

Зафиксировать остановку отправителей/cron и отсутствие операций в полёте; применить guard → pin → явное sandbox в порядке manifest. Нельзя переключать среду одновременно с работающими отправителями. После отдельно разрешённого выпуска проверить настоящий Auth/RPC, существующие заказы, получение статусов и восстановление. Новую оплату или возврат не создавать как неявную проверку. SQL-кандидаты до готовности процедуры остаются вне supabase/migrations.

### 3. Реализовать production-контракты и адаптеры

Следовать 05.2–05.4 в [дизайне](PROD-PAY-05-design.md): отдельные серверные точки входа и область магазина, production-хранилище/RPC, серверные цена и документы, ручная месячная подписка, идемпотентное восстановление. Клиент не выбирает среду. Recurring не входит в первый продукт. Существующие sandbox-обработчики нельзя просто направить на боевой магазин. Default флаги отправок выключены.

### 4. Сформировать исполнимый пакет без продаж

После совместимости зафиксировать SHA, migration/function manifest, allowlist проекта, concurrency и предварительные проверки. Установка расширений и её ограничения описаны [отдельно](PROD-PAY-05-extension-prerequisites.md). Проверить реальные полномочия hosted postgres, версии/ACL расширений, чистое состояние оплат и неактивные jobs. Локальный postgres-superuser не заменяет эту проверку. Общий deploy-production.yml не использовать как готовый платёжный release workflow.

### 5. Выпуск и приёмка

После отдельного разрешения опубликовать совместимый пакет с выключенной отправкой; проверить роли, конфигурацию, очереди, мониторинг и HTTP-поведение. Только затем решать о включении продаж и конкретной реальной операции по критериям 01–08. До этого зелёные локальные тесты не означают готовность оплаты на production.

## Содержимое 99 миграций сопоставлено — 01.10.2026

Источник: SQL Editor https://supabase.com/dashboard/project/szjiwamevblkpjmmeonf/sql/fcf7caa3-d17f-48be-855b-628f70e34f8a. Выполнен SELECT version,statements FROM supabase_migrations.schema_migrations ORDER BY version в READ ONLY транзакции с statement_timeout=20s и ROLLBACK. Получено 99 строк. Download CSV завис и не дал подтверждённого файла; после восстановления инструмента Export → Copy as JSON вернул все 99 записей (409465 символов JSON). Сырые SQL-тексты не добавлены в репозиторий.

Локальный инструмент `node scripts/migration-statement-comparison.js` разбивает проверенные исторические файлы на операторы, сохраняя комментарии, содержимое кавычек и dollar-quoted тел. Нормализация: CRLF → LF и trim только краёв отдельного оператора; разделительные точки с запятой в локальном файле не включаются, как в сохранённом массиве statements. Внутренние пробелы, регистр и порядок сохраняются. Это узкий лексический инструмент для текущего baseline, не полноценный PostgreSQL parser и не исполнитель SQL. Неоднозначные backslash-escape и незакрытые конструкции отклоняются; поддержку нового синтаксиса нельзя предполагать автоматически.

Алгоритм: SHA-256 от JSON.stringify массива операторов для каждой версии; затем SHA-256 от строк version:hash, упорядоченных по версии и соединённых LF без завершающего LF. В браузерной сессии расчёт выполнялся по JSON штатного экспорта через Web Crypto, локально — node:crypto. Оба результата: 99 записей, aggregate `f4f3d6b2291de6bcda5947256c69123fd4da5aad86cd71809972a328c72df1bd`. Совпадение подтверждено программным сравнением. Изначальный консервативный отказ на regex-строках трёх файлов устранён без изменения SQL: обратный слеш перед точкой не меняет границу строкового литерала.

Проверки: 31 тест PASS (12 тестов разбивки/сохранения SQL и 19 тестов планировщика), lint/build PASS с прежними React-предупреждениями. Добавлены scripts/migration-statement-comparison.js и scripts/migration-statement-comparison.test.js; обновлён этот отчёт и production-baseline. Commit/push/deploy не выполнялись.

Закрыта сверка содержимого журнала для этого снимка. Совпадение истории не доказывает отсутствие ручных изменений фактической схемы. Следующий шаг — read-only инвентаризация текущих объектов/ACL/RLS и сравнение с реконструированным baseline на одноразовой БД. Планировщик без отдельного доказательства по-прежнему выводит remoteContentsVerified=false: его вход содержит только версии, поэтому переносить в него положительный результат из чата автоматически нельзя.
