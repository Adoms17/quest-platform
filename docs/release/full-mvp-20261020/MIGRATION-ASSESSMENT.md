# Оценка 228 миграций для полного MVP

Дата: 20 октября 2026. Источник — PR183 head
`6a654dc5738ff0c81bf31616c50a2a6c167c3b11`. Это анализ исходников,
не выполнение SQL и не разрешение применять каталог миграций.

Проверяемые результаты: [все 228 строк](MIGRATION-REGISTER.md),
[JSON с хешами, операторами, зависимостями и рисками](migration-assessment.json),
[генератор только для чтения SQL](generate-migration-assessment.py).
Генератор сверяет нормализованные SHA-256 всех 327 исходных SQL с существующим
source-manifest; никакие SQL, сеть, переменные окружения или команды процессов не запускает.
Его запуск создаёт только эти два документа. Runtime, workflow и исходные миграции неизменны.

## Состав и метод

Сохранённый production ledger содержит 99 версий до `20260914210000` включительно.
Их точное множество было подтверждено read-only list_migrations 20 октября в
предыдущем preflight. Это не подтверждение тел функций, таблиц, расширений,
эффективных прав или данных текущей production БД. Нового чтения БД здесь нет.
Оставшиеся 228 версий — разность множеств, а не автоматически разрешённый backlog SQL.

| Основной тип (один на файл) | Файлов |
|---|---:|
| Schema: таблицы, столбцы, ограничения, индексы, триггеры | 101 |
| Определения/замены функций | 98 |
| Seed: исходные справочники, permissions, bucket | 13 |
| Backfill существующих строк/проекций | 12 |
| Cron с сопутствующей схемой/функциями | 3 |
| Поддержка приёмочной fixture | 1 |
| **Всего** | **228** |

Типы пересекаются: schema есть в 129 файлах, функции в 227, permissions в 208,
непосредственные операции с данными в 25 (12 backfill и 14 seed, один файл содержит оба),
cron в 3. Нет отдельного файла только с permissions: такие изменения включены в
другие категории. Seed здесь не означает демонстрационные данные или разрешение их вставки.

56 файлов меняют существующие тела через `pg_get_functiondef` и строковые замены.
`UPDATE` внутри создаваемой функции не является выполненным backfill. Это отделено
от 25 файлов с top-level DML. DO-предусловие в `20260920080000` проверяет наличие
legacy promotions и останавливает удаление при несовместимых данных.

Разбор лексический, не полноценный PostgreSQL parser. Он читает все файлы и
отделяет SQL-операторы по кавычкам/dollar-body/comments. `lexicalPriorProviders`
показывает предыдущую исходную миграцию, определяющую упомянутый объект; это
консервативная подсказка, не полный runtime-граф. Отдельно сохранены сигнатуры
строковых замен и предыдущая версия исходного порядка. Имена overload-функций
в графе объединены, динамический SQL/неявные объекты требуют отдельной проверки.
Удаление объектов и транзитивные зависимости не моделируются. Удаление комментариев
не реализует все правила строк SQL, а scanner не поддерживает все варианты E-string;
review не обнаружил вызванного этим искажения классификации текущих 228 файлов.

Восемь нераспознанных лексически имён объясняются исходниками, а не доказанным
отсутствием объектов: семь `*_id_seq` возникают у identity-столбцов;
`platform_private.reserve_linked_subscription_fiscal_refund` создаётся заменой
имени в определении функции в `20260928012000`, строка 49. В JSON эти ограничения
сохранены, чтобы не выдавать извлечение имён за доказательство полного графа.
Auth/Storage/extensions и фактический production-каталог этим графом не аттестованы.

## Данные и специальные случаи, требующие решения

- `15010000` (дата 202609): seed Free/Pro/Business с лимитами; `16003000` — grace 120 часов.
  Эти значения не становятся утверждёнными production условиями из-за присутствия SQL.
- `15020000`: явная блокировка organizations и backfill подписок в `transition`;
  требуется согласовать переход существующих организаций, длительность блокировки и последствия квот.
- `15120000`: начало покрытия usage фиксируется временем применения; это не восстановление старой статистики.
- `15180000`/`15200000`: пометки stale для scheduled/cancel intents;
  `16020000`/`16021000`: восстановление trial started/duration.
- `18010000` и seed-файлы `19010000`, `21020000`, `21030000`, `21050000`,
  `22010000`, `22020000`, `25010000`, `25020000`, `25030000`: роли/permissions.
  Они не создают разрешение назначить реального администратора или bootstrap owner.
- `20010000`, `20130000`, `20270000`: timeline, состояния checkout, materialized тарифы;
  нужны отсутствие конфликтов и сохранение уже принятых условий.
- `25025000`: activity backfill с estimated временем из attempts/events;
  `25045000`: перенос trial paid-period slots; нужны согласованность ссылок и повторяемость.
- `26038000`: backfill monthly prices (0 / 99000 / 249000 minor units) в трёх таблицах;
  это явное бизнес-решение о ценах, не технический default для молчаливого применения.
- `20261006010000`: приватный bucket participant-avatars с PNG/лимитом 1 MiB,
  policies и функции профилей; проверить существующий bucket/политику хранения.
- `20260928018000`: создаёт поддержку fiscal acceptance fixture, а не вставляет
  готовые тестовые заказы. Нужен отдельный выбор production-размещения этого инструмента.

Три cron-миграции (`20260916010000`, `20260924010000`, `20260930020000`)
создают задания, затем ставят `active=false`. Это не разрешение применять их:
два задания явно stage-specific, а в settlement есть sandbox shop contract.
`20260924020000` меняет подпись scheduled requests через замену функции.
Нужно отдельно утвердить production endpoints/token scope и доказать OFF перед применением.
Сам анализ не читает token values и не создаёт секреты. Расширения добавляются в
`16010000` (pg_cron) и `24010000` (pg_net, supabase_vault); их live состояние UNKNOWN.

## Решения до применения

| ID | Конкретное недостающее решение/доказательство |
|---|---|
| D1 | Подтвердить каталог/сигнатуры/расширения production относительно ledger99; определить обработку drift, не считать ledger хешем схемы. |
| D2 | Утвердить production mapping каждой строки: исторический файл, специально подготовленная миграция или инструмент stage/приёмки. После этого зафиксировать applyOrder и хеши; сейчас все HOLD. |
| D3 | Утвердить итоговые grants/RLS/SECURITY DEFINER и назначения ролей отдельно. Анализ не разрешает менять ACL/auth. |
| D4 | Утвердить seed/backfill значения, условия отбора и preconditions для существующих строк, блокировки, восстановление и идемпотентность. Особенно transition, цены, permissions, bucket. |
| D5 | Определить production замену stage cron/endpoint/shop contract, extension prerequisites и порядок создания в OFF; активация отдельно. |
| D6 | Решить, где допустим acceptance-fixture инструмент; исключение из production SQL не означает урезание продуктового scope. |
| D7 | Связать итоговые RPC/Edge/frontend контракты с точным SHOP source bundle; подтвердить sandbox→production mapping без автоматического переноса dirty/UNAPPLIED. |
| D8 | Утвердить совместимый rollback code/artifacts и проверенный restore point до изменения данных; определить границу необратимых внешних операций. |

DDL может брать блокировки, новые constraints могут отклонить старые строки,
замены RPC меняют поведение уже работающего frontend/worker. Откат frontend не
отменяет backfill и внешние платежные обязательства. Reverse SQL и restore не
подготовлены и не разрешены. Для несовместимых форматов сначала останавливают новые
операции по отдельно утверждённому плану, сохраняют очереди/обязательства и выбирают
совместимое исправление; слепой rollback недопустим.

## Ближайший исполнимый шаг

Продолжить статическую подготовку production mapping D2 на базе этого реестра:
начать с 25 файлов данных, трёх cron, fixture и 56 точных function-body patches,
зафиксировав разрешённый контракт и preconditions для каждого. Параллельно можно
подготовить отдельный review включения восьми доказательно локализованных SHOP
исходников из [SHOP review](SHOP-SOURCE-REVIEW.md), учитывая общих потребителей handler.
Это работа с документами/исходниками, не разрешение применять SQL или менять runtime сейчас.
Создание ресурсов, настройка секретов/доступов, ACL, production SQL, merge/deploy
требуют отдельного конкретного допуска. B17 и commercial gates остаются отдельно;
данный анализ их не закрывает.
