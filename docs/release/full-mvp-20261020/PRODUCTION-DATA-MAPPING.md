## Итоговые технические предложения

1. Сохранить существующие условия: transition без новой даты истечения; отсутствующая
   подписка не становится Free/paid. На границе применения не перезаписывать существующую
   строку subscription. Quota enforcement и lifecycle activation не следуют из seed.
2. Использовать уже утверждённые начальные цены и сохранённые версии, не смешивать
   stage offer с публичной ценой и не переписывать оплаченные условия. В отличие от
   первой общей оценки, отдельного согласования 990/2490 здесь не требуется.
3. Перенести справочник разрешений как реализованный контракт, но сохранить пустой
   набор новых реальных назначений. Bootstrap owner, ACL/RLS apply и grants — только
   в отдельно разрешённом исполнении; seed роли не является таким разрешением.
4. Два stage HTTP scheduler требуют нового проверенного production mapping, а не
   применения исторического SQL как есть. Полный продуктовый scope сохраняется;
   выключенное расписание не заменяет готовность reconciliation/settlement.
5. Fixture не использовать для коммерческой публикации. Её исходник и реализованные
   продуктовые refund/fiscal функции остаются в интеграционном scope.

Статическая проверка дополнительно нашла имя fixture-таблицы в
`scripts/production-environment-pin.candidate.sql:17` и guard-adoption candidate:
они проверяют наличие истории в существующих relations перед назначением среды.
Это не вызов создания fixture, но причина **не удалять её схему автоматически**
по одному признаку «tooling». Возможное сохранение пустой закрытой структуры и
guard совместимости рассматривается в SQL mapping отдельно от допуска её использования.
В обычных бизнес-исходниках App/Edge прямой вызов prepare_fiscal_acceptance_fixture
не найден; приёмочный Admin API и stage scripts существуют. Поиск имён не является
полным доказательством отсутствия динамической зависимости.

## Следующий конкретный исполнимый шаг

Подготовить **неисполняемый production binding manifest** для двух HTTP scheduler:
явные поля endpoint origin/handler, merchant/fiscal policy reference, secret-name,
HMAC contract, OFF/empty allowlist и перечисленные ограничения. Заполнить из
существующих утверждённых источников; неизвестные поля оставить null с владельцем
решения. Одновременно статически проверить, что fixture не входит в dependency
closure бизнес-RPC. Это не создание секретов/ресурсов и не SQL.

Перед любым применением отдельно нужны свежие технические evidence каталога/данных,
совместимый SQL mapping, порядок, lock budget и restore/rollback. Исторический PASS
и эта матрица не заменяют эти доказательства. B17 не запускался и не закрыт.
